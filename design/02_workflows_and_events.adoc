== Workflow Catalog

Six business workflows (W1–W6), two supporting workflows (S1, S2), and the cross-cutting
layers of chapters 10–15. Each workflow is an event-flow narrative; "built in" lists the chapters that
construct it — a workflow built across several chapters is the norm, and is the evolutionary
architecture working as promised. Event names are defined in the catalog at the end of this
document.

=== W1 — Trip Booking (the spine)

The one workflow that runs through the whole book. Every part extends it rather than replacing
it.

*End-state flow:*

1. `TripRequested` (Booking Agent, from the UI chat — or from the Semantic Router when the
   request arrives by email; in ch 1, the demo script publishes it directly).
2. For a simple trip, the Itinerary Planner Agent consumes it, consults the Destination Research
   Agent, checks availability on the Airline Booking System sim, and publishes
   `ItineraryProposed`.
3. For a multi-item trip, the Trip Coordinator instead fans out `FlightSearchRequested` /
   `HotelSearchRequested`; the airline and hotel agents answer with `FlightOffersProposed` /
   `HotelOffersProposed`; the barrier releases `ItineraryAssembled`; conflicting details go
   through `ActionProposed` → `ActionCommitted` (Arbiter).
4. The customer accepts: `ItineraryApproved` (via UI). The Policy Gate checks the B2B client's
   rules and either stays silent or opens the approval workflow (W4).
5. The Coordinator's deterministic booking step calls the airline and hotel booking systems:
   `FlightBooked`, `HotelBooked`. The Rental Car Agent reacts to `FlightBooked` by pure
   choreography: a pay-later `CarRentalReserved` in the requested class with its estimated
   total, or `CarRentalUnavailable` when no class fits.
6. The Coordinator's payment step publishes `PaymentRequested` and charges the Payment sim under
   an idempotency key: `PaymentAuthorized`.
7. `TripConfirmed` (Coordinator); the Booking Agent relays it to the customer.

*Built in:* ch 1 (steps 1–2 decoupled as a round trip — the demo script publishes
`TripRequested` and receives `ItineraryProposed`, matching on the request event's id; audit
consumer), ch 2 (CloudEvents contracts, correlation and causation), ch 3 (planning against the
airline booking system), ch 7 (step 3, step 5 without approval), ch 8 (steps 4 and 7), ch 10 (step 6 made idempotent).

=== W2 — Inbound Email Triage

Email arrives in volume; most of it must never reach an expensive agent.

*Flow:* `EmailReceived` (replay script over the seeded dataset) → the Semantic Router buffers
each burst in a short time window and classifies the batch in one bulk call (semantic
windowing) → republishes a typed business event of its own context (`TripRequestReceived`, a provisional name settled at
ch 4's planning, `SupportRequested`, `VendorUpdateReceived`; the Booking Agent turns the first into `TripRequested`, since
`booking.TripRequested` has one owning context), stripping the raw email (headers, quoted chains) down to the fields
downstream agents need (payload mediation) — or drops spam at the Token Defense Filter → an
out-of-order vendor
update (a hotel confirmation arriving before its prerequisite flight confirmation) is staged in
the `InboxStore` until the prerequisite arrives. Support requests flow on to the external
Support Desk AaaS sim via Deterministic Edge Prompting (`SupportTicketResolved` comes back).

*Built in:* ch 4 (support integration itself from ch 3).

=== W3 — Destination Research and Content Ingestion

*Flow:* `BrochureUploaded` (UI or script) → PDF stored via `BlobStore` → `DocumentAvailable`
carrying only the claim reference → Destination Research Agent (LlamaIndex) indexes it →
planning queries answer from indexed knowledge.

*Built in:* ch 5 (claim check); the agent itself from ch 3.

=== W4 — B2B Policy and Approval

*Flow:* `PolicyViolationDetected` (Policy Gate; e.g., a flight over $1000 for the B2B client) →
the Coordinator saves `WAITING_FOR_APPROVAL` and emits `ApprovalRequested` **atomically via the
Agentic Outbox**, carrying the semantic checkpoint (reasoning snapshot) → the manager decides in
the approval console → `ApprovalGranted` / `ApprovalRejected`; or the `EventScheduler` fires
`ApprovalTimedOut` after 48 h → escalation. A stale approval arriving after the timeout is the
ABA demonstration. Ch 13 hardens the same gate against injected prompts and blinds the search
agents to payment data (contextual segregation).

*Built in:* ch 8 (ch 13 hardening).

=== W5 — Disruption and Compensation Saga

The unhappy path as a business reality: the trip is partly booked and the world changes.

*Flow:* the manager approves, the flight books — then the Hotel Booking System sim's scripted
`HotelSoldOut` arrives. The Cleanup Agent (LangGraph) catches the failure event, assesses the trip, and drafts
`CancellationDrafted` (a nuanced customer email and cancellation plan); deterministic
compensation code executes the mutations — cancelling the flight on the airline booking system
(`FlightBookingCancelled`) — and the Coordinator closes the workflow with `TripCancelled`. If
the Hotel Agent's rebooking negotiation with the hotel booking system's scripted auto-responder loops,
the livelock breaker
increments `negotiation_turn_count` in the `WorkflowStateStore` and terminates the loop into the
same compensation path. The circular wait between the parallel flight and hotel sub-workflows is
the ch 9 deadlock demo.

*Built in:* ch 9 (on ch 8's machinery).

=== W6 — Failure Recovery and Replay

*Flow:* a malformed booking confirmation (poison pill) crashes the CrewAI Hotel Agent →
the event lands on the DLQ → the bug is fixed → the same pure business event is replayed
to a LangGraph-built replacement agent, which finishes the trip. Separately, a duplicate
delivery of `PaymentRequested` is absorbed by an `IdempotencyStore` check before the Payment sim
is charged twice.

*Built in:* ch 10.

=== S1 — Trip Memory and Context (supporting workflow)

*Flow:* all W1 events → Observer/Reflector Agent projects `TripView` upserts into the
`SemanticViewStore` → any waking agent hydrates by `correlation_id` / `context_path`
(Tier 1 + Tier 2) instead of replaying history. Ch 5's A/B compares the summarizing and
experiential variants of the same Observer; ch 7 scopes views by `context_path` so the Paris
Hotel work never sees Madrid's events.

*Built in:* ch 5 (variants), ch 6 (CQRS + hydration), ch 7 (context paths).

=== S2 — Duty of Care (supporting workflow)

*Flow:* `DutyOfCareSweepDue` (EventScheduler, recurring) → the Duty-of-Care Monitor queries
the Travel Advisory Feed sim for advisories touching booked destinations →
`TravelRiskDetected` on impact → the Booking Agent warns the customer; a disruptive
advisory can open the W5 compensation path. The Booking Agent's follow-up nudge shares the
mechanism: `CustomerFollowUpDue`, scheduled when a proposal is relayed, triggers a reminder
if the customer has not answered.

*Built in:* ch 8.

=== Cross-cutting layers (ch 10–15)

Not workflows but behaviors applied across W1–W6:

* **Reliability (ch 10):** DLQ routing and replay (W6), idempotent side-effects.
* **Cost governance (ch 11):** token budget per `correlation_id` in the `WorkflowStateStore` →
  `BudgetExceeded` throttles; LiteLLM's configured fallback chain (cloud → local Ollama) engages
  on provider outage or budget downgrade, and a LiteLLM callback publishes
  `ModelFallbackActivated` so the fallback is a visible business fact, not a silent retry.
* **Testing (ch 12):** the whole system exercised offline — `InMemoryBroker`, deterministic LLM
  fixtures, LLM-as-judge regression scoring, a shadow consumer.
* **Security (ch 13):** Guardrail Worker republish-or-quarantine (`EventQuarantined`), egress
  DLP scrubbing, Policy Gate as the deterministic last line, red-team script.
* **Observability and evolution (ch 14):** OTel spans (`llm.token_count`,
  `agent.reasoning_step`) across W1 end to end; V1→V2 schema Translator.
* **Cloud (ch 15):** every Port re-implemented against managed services; the same workflows
  under load and chaos.

== Draft Event Catalog

Conventions:

* Names are **PascalCase past-tense business facts** (`FlightBooked`), never commands.
* On the wire every event is a CloudEvent; `type` is
  `<domain>.<Name>` (e.g. `booking.TripRequested`), where
  `<domain>` is the bounded context, the catalog's group headers below; the domain map in
  01_system_overview.adoc is the authority, and `system` is the technical namespace outside it. The book's prose uses
  the same qualified form. Payload schemas are Pydantic models (ch 2.5); this catalog fixes names and
  ownership, not field lists — full contract detail would be invalidated by chapter-level
  discoveries.
* Every event carries `correlation_id` (from ch 2) and `context_path` (from ch 7) as
  CloudEvents extension attributes; the full identity conventions — UUID event ids,
  causation, order id — are the Identifiers section of 01_system_overview.adoc.
* One producer per event type (single writer); consumers listed are typical, not exclusive —
  the audit consumer and Observer see everything via the port's subscribe-all capability
  (01_system_overview.adoc, Ports).

Notes:

* Chapter 1 publishes two event types — `TripRequested` (demo script → Planner + audit) and
  `ItineraryProposed` (Planner → the script) — the reply carrying the request event's id as
  a `request_id` payload field, promoted to a `causationid` extension attribute in ch 2.6.
* DLQ and replay are broker-contract behavior (ch 10), not separate event types: dead-lettered
  events are the original business events on a DLQ topic.
