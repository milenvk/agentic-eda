== Two Packages: the Framework and the Application

The repository holds two libraries, and the line between them is the line between what any
agentic event-driven application needs and what only a travel agency needs.

* **`agentic_eda`, the framework** (`lib/agentic_eda/`, distributed as `agentic-eda`): the
  `EventBroker` port and its adapters, the per-key lanes, `connect`, `envelope` (the
  `ContextAttributes` the port and the contracts both import, so neither imports the other),
  the `@event` machinery (`EventContract`, `Nothing`, `OWN_ID`, `data_of`), the agent activator with its framework
  adapters, the `eda` face imported by a developer, every other port with its adapters
  (hydration, the view store, the artifact store), producer identity's signing and
  verification, the supplier client's circuit breaker, the replay module, and the `console`
  event renderer.
* **`travel_agency`, the application's shared code** (`lib/travel_agency/`, distributed as
  `travel-agency`): the event-type constants, the catalog as code (one module of `@event`
  classes per context), the value objects every context shares, the registry of the
  components' public keys, and the `sims` package holding the simulators' world seed. It is
  the domain map's shared kernel as code, with one guest: the world seed belongs to the
  suppliers' side, is shipped here because the simulators are part of this repository, and
  is imported by the simulators and by tests, never by an agent.

The test for where a module goes: a team building a different business would use it
unchanged, or it names something of this business (a trip, a supplier, an event type). The
first kind is the framework's, the second the application's, and a module that is both is
split.

The dependency runs one way. `travel_agency` and every component import `agentic_eda`, and
`agentic_eda` imports neither. The rule is kept by construction, not by review: the
framework's suite, `tests-agentic-eda`, runs in an image holding the framework alone
(`docker/agentic_eda.Dockerfile`), so an import of the application fails the gate. For the
same reason the framework's tests declare example events of their own. Its docstrings stay
on the book's running example, because an illustration is not a dependency and one example
across the book and the code is easier on the reader than two.

What the framework reads from its surroundings is configuration, never an import: the
broker's address, a component's name (`COMPONENT_NAME`), an adapter's choice
(`HYDRATION_ADAPTER`), and from ch 13 the path of the key registry, which is the
application's data handed to the framework's verifier.

A reader building their own application takes the framework and leaves the agency: they
install `agentic-eda` from this repository
(`pip install "agentic-eda @ git+https://github.com/milenvk/agentic-eda#subdirectory=lib/agentic_eda"`),
write their own event-type constants and `@event` classes, and attach the activator to the
app hosting their agent. The repository README says so, and says what the framework is: the
book's reference implementation, with each chapter teaching one part of its inside, and no
promise of a release cycle.

`starter/` is that path, already walked: the smallest application on the framework, in a
business that is not travel (a shop's product reviews, triaged by one agent). It holds one
consumed and one produced `@event` class, one agent written as a plain async function with
no agent framework, no broker, and no envelope in it, the FastAPI app with the one `attach`
line, a script publishing a review and waiting for its triage, a compose file with Kafka,
and one test behind a `compose.tests.yaml` of its own. It imports `agentic_eda` and never
`travel_agency`, its image holds the framework alone, and it follows the application's
division of labour: the model judges and code carries the facts. Its README is a
walkthrough for making it one's own (rename, replace the two events, replace the agent) and
for taking it out of this repository, where the framework is installed from the
repository's GitHub archive (no `git` is needed in the image) instead of from the tree.
`starter/test.sh` is its gate, run with the chapters' gates.

== The `EventBroker` Surface, Final Form

One tree means one framework, so the public surface is designed complete up front and is
**frozen for the whole book**: the book's listings and the repository never drift. Adapter
internals may mature chapter by chapter; these signatures do not.

[source,python]
----
class ContextAttributes(BaseModel, extra="allow", frozen=True):
    specversion: Literal["1.0"] = "1.0"
    id: str                          # UUID, globally unique across the whole system
    type: str                        # domain-prefixed name, e.g. "booking.TripRequested"
    source: str                      # who published it
    time: datetime | None = None
    datacontenttype: str | None = None
    dataschema: str | None = None
    subject: str | None = None
    __pydantic_extra__: dict[str, str | int | bool] = Field(init=False)  # extensions, by name

class WireEvent(ContextAttributes):
    data: dict                       # the business fact

class EventBroker(Protocol):
    async def publish(
        self, event_type: str, source: str, data: dict,
        id: str | None = None, attributes: dict[str, str] | None = None,
    ) -> WireEvent: ...
    async def subscribe(
        self, event_type: str, handler: EventHandler, mode: str = "broadcast"
    ) -> None: ...
----

* `publish` returns the event as published, so a caller sees what the broker filled in as well
  as what it passed: the id whether generated or supplied, the time, and the rest of the envelope.
  Its `attributes` argument carries the optional and extension attributes a caller supplies.
* `handler` is an async callable receiving an `WireEvent`, which reads every attribute by name:
  `event.id`, `event.time`, an extension as `event.correlationid`, and the business fact as
  `event.data`.
* The shape is CloudEvents' own. A structured CloudEvent is flat, its context attributes beside
  `data`, and so is `WireEvent`; the CloudEvents SDK's Pydantic event implements extensions the
  same way, through `extra="allow"`. One class, `ContextAttributes`, is therefore the attributes
  on the wire, in the port, and in the agent's view (`attributes_`, The Agent Activator), and
  nothing converts between them. Both classes are frozen, so no handler alters a delivered
  event. Extension values are `str | int | bool` because the spec allows integer and boolean
  extensions and a producer outside the book may send one; the book's own are strings.
* Deferred capabilities carried by the frozen surface: `attributes` is exercised from ch 2
  (CloudEvents, `correlationid`, `causationid`, and `partitionkey`), `mode="competing"` and the
  `"*"` subscribe-all sentinel from ch 4. Ch 1 code uses none of them, and the adapter
  underneath is already the production-shaped one (one topic per context, per-key lanes):
  ch 1 prints none of its internals, so nothing in the chapter changes when they are taught.
* The port has no nack, no defer, and no key parameter. Returning from a handler acknowledges;
  raising redelivers under at-least-once; the key travels in `attributes`, under the name the
  port module states once as `PARTITION_KEY`, so producers and adapters never spell it twice.
  Everything left unsaid by the port is the adapter's or the activator's business (below).

=== Ports are `typing.Protocol` (PEP 544)

Structural subtyping: an adapter satisfies a port by method shape alone, with no inheritance,
and the adapter never imports the port. Agents type-hint against the Protocol; any object
with the right methods qualifies (the Kafka adapter, the ch 3 `InMemoryBroker`, a test
double). This is the ports-and-adapters dependency direction expressed in Python's own
idiom: agents depend on the port, adapters depend on nothing from the agents' world.

=== Opening a broker

`connect.event_broker(client_name, start="now")` is an async context manager and the only
place any component names an implementation. The activator calls it when the app it is
attached to starts (The Agent Activator, below), and ch 1's components, which predate the
activator, call it in their own entry points; none of them imports an adapter, reads a broker address, or closes a
connection. A second broker, or a test double, is a change to that one function.

It yields an `EventBrokerConnection`: the frozen `EventBroker` surface plus `run()`, the delivery
loop; a process hands control to it after subscribing. The split is the dependency
rule made visible. Business logic type-hints `EventBroker`, because publishing and
subscribing is all it ever does; only the entry point needs the loop. Lifecycle stays off
both surfaces, because the factory owns it.

=== Generation rules

`publish` completes whatever the caller omits, so every event is spec-complete no matter how
little is passed:

* `id`: a UUID. Ids are globally unique across the entire solution by architectural
  decision (see Identifiers in `01_system_overview.adoc`), deliberately stricter than the
  CloudEvents per-`source` minimum.
* `time`: now, UTC, unless supplied in `attributes`; RFC 3339 on the wire.
* `datacontenttype`: `application/json` unless supplied in `attributes`.
* `specversion`: declared on `ContextAttributes` as `Literal["1.0"]` with that default, so no
  caller sets it, and an event of another spec version is rejected when it is decoded.
* `partitionkey` is never generated from nothing. It is the value of the field the event's class
  declares with `order_per` (The Agent Activator, below), because only the producer's side
  knows the aggregate; a key unique per event would be no order at all. From the ch 2
  practical the activator fills it on every publish, and `consumes` and `produces` refuse a
  class that declares nothing, at import; a class declaring `order_per=None` is published with a null key, as ch
  1's events are, and `order_per=OWN_ID` keys the event that starts a sequence on its own
  generated id.

=== Attributes

An `WireEvent` carries the declared context attributes (`specversion`, `id`, `type`, `source`,
`time`, `datacontenttype`, `dataschema`, `subject`), the extension attributes as extras read
by name, and `data`. A new extension needs no change to any class. The extension attributes,
in order of introduction:

* `correlationid` (ch 2): the execution thread's label, the conversation's id, generated at the
  first customer message (or by the demo script standing in for it) and copied to every event
  of the execution.
* `causationid` (ch 2): the id of the event that directly caused this one.
* `partitionkey` (the ch 2 practical): the standard CloudEvents partitioning extension, on
  every event; the id of the event's aggregate: the trip's id on booking, planning, and policy
  facts, the conversation's id on customer facts, and, where the context holds no aggregate,
  the id of the trip concerned or, before a trip exists, the conversation's. On
  `booking.TripRequested` it is the conversation's id, and `booking.TripCreated` is the first
  event keyed by the trip's. The adapter maps it to whatever its broker
  orders by (Ordering, below).
* `contextpath` (ch 7): hierarchical context scoping, `/trips/{trip_id}/paris/hotel`.
* `promptversion` and `modelversion` (ch 10): stamped by the activator on every event an agent
  publishes, from the agent's own configuration (Prompts as configuration, below). No consumer
  acts on them; the dead-letter tooling, the replay script, and the audit record read them.
* `identitytoken` (ch 13): the producer's signed identity (Producer Identity, below).

== Wire Format

CloudEvents 1.0 **structured JSON** from day one, encoded and decoded by the CloudEvents
Python SDK (`cloudevents`, pinned at 2.2.0) inside the adapter. Components never see bytes,
and no component or listing imports the SDK. The Kafka adapter turns an `WireEvent` into the SDK's
`CloudEvent` (its attributes from `model_dump(exclude={"data"})`, and its data) and writes it
with the SDK's Kafka binding in structured mode: the record's value is the JSON, its
`content-type` header is `application/cloudevents+json`, and its key is the `partitionkey`
extension, the binding's default key. Decoding goes through the binding's auto-detecting
read, so an event arriving in binary mode (`ce_` headers) from a producer outside the book
decodes too, and the SDK's attributes and data become an `WireEvent` one to one. The SDK is pinned
exactly because its 2.x line warns that it "will break with every update": the adapter's
tests catch a break before an upgrade ships, and the break stays inside the adapter. The
push route (ch 15) uses the SDK's HTTP binding the same way.

== Event Type Naming

* An event type is `<domain>.<Name>`, where `<domain>` is the bounded context (the catalog
  groups in `02_workflows_and_events.adoc`: `customer`, `planning`, `booking`, `policy`,
  `servicing`, `support`, `destination`, and the technical namespace `system`). There is no
  organization segment: the domain is what a reader and a subscriber need, and a reverse-DNS
  prefix adds length without adding meaning inside one system.
* Every type is declared exactly once, as a constant in
  `travel_agency/event_types.py`, grown additively by later chapters. Components import
  the constant, never retype the string. From ch 2 the type's `@event` class binds to that
  constant (The Agent Activator, below), so the type is still spelled once and its class is
  found from it.
* The producer is **never** part of the type. Its identity is carried by the CloudEvents
  `source` attribute; the Single Writer Principle assigns one owning context per type, a
  producer stands in that context, and a relay publishing for an owner (the `EventScheduler`,
  the outbox relay) sets `source` to that owner. A context's requests (its open-host published
  language: `booking.TripRequested`, `booking.CustomerReplied`, `planning.ItineraryRequested`,
  `support.SupportRequested`, `destination.InspirationRequested`) are written by whoever asks,
  and the catalog marks them. The book replaces a producer behind stable events (ch 2) and
  adds callers of a published language (ch 3, 4, 14), and producer-named types would break
  both.
* Quoting registers: code uses the full string; repository documentation (chapter READMEs,
  design docs where disambiguation helps) quotes domain-qualified, `booking.TripRequested`;
  book prose uses the same domain-qualified form.

== Topic Mapping

`topic_for(event_type)` in the Kafka adapter is the one place a topic is named; agents never
name one. The mapping is the same from ch 1 to the end of the book, and the port never sees it.

* **One topic per context.** `topic_for` returns the type's prefix, so the `booking` topic
  carries every booking event, and likewise for the other six contexts and for `system`. The
  type travels inside the event (CloudEvents `type`); a subscription by type is filtered in
  the adapter, which subscribes to the context topic behind each subscribed type, dispatches
  by type, and acknowledges events of other types without handing them to a handler. The
  reason is the ordering contract: an ordering broker orders per key within one topic, so two
  events of one aggregate on two topics are unordered whatever their key. One topic per
  context is the first of the contract's three conditions
  (`05_data_consistency_and_state_model.adoc`). Ch 1 shows the mapping in one listing and
  says why in one sentence; the record key is null until the ch 2 practical introduces
  `partitionkey`.
* **Subscribe-all** is a regex subscription over the seven context topics and `system`; a
  new event type never creates a topic, so the audit consumer sees it with no discovery
  delay.
* **Dead letters** (ch 10) go to one DLQ topic per context, `dlq.<context>`, with the record
  key preserved, so a replay from the DLQ keeps per-key order.

== Subscription Mechanics (Kafka adapter)

* Consumer group id = the adapter's `client_name`. Distinct components therefore each
  receive every event (broadcast across components), while replicas sharing a `client_name`
  compete within one group; the two `mode` semantics fall out of group identity.
* Offsets are committed manually, **only after the handler returns**
  (`enable_auto_commit=False`), and only up to the watermark (the consumer rule, below). A
  consumer killed mid-handler never commits, so the event is redelivered on restart: the ch 1
  durability demonstration, and the at-least-once floor the book teaches in
  `ch02_delivery_guarantees`.
* `event_broker(client_name, start=...)` chooses where a component reads from the first
  time it subscribes, and `start` has exactly two values.
+
--
`"now"` (the default) delivers what is published from that moment onward. It is the one promise kept
by every broker, so a component that says nothing about history behaves
identically on Kafka, Pub/Sub, and RabbitMQ Streams.

`"beginning"` asks for the history still held by the broker, which only a log-backed broker can
serve. An adapter that cannot replay must raise rather than quietly starting from now: silently
downgrading the caller's one explicit request is the failure mode, and this option exists to prevent
it. "Beginning" means the start of the *retained* log, not the start
of time, and Kafka's `log.retention.hours` defaults to 168.

The option is on the connection because a component is one consumer group, and Kafka fixes
the starting position per consumer. It has no effect once a group has read anything, since
from then on the component resumes from its own committed position.
--
* Ch 1 uses the default throughout, so the audit consumer sees only what follows it. The
  patterns that need history ask for it in their own code: event sourcing (ch 6) and time
  travel (ch 10).
* One Kafka detail the port does not hide: redelivery of an unacknowledged event depends
  on the group having committed at least once. A group killed before its first commit has
  no committed offset, so it resets by `start` and the in-flight event is skipped. Every
  event after that is redelivered as promised. Ch 1's demo is unaffected because act 1
  completes a round trip before act 2 kills anything, and a queue-backed adapter has no
  equivalent gap, since its queue exists from the moment of binding.

=== Ordering: the contract and how the adapter keeps it

The contract (ch 2.6, from the ch 2 practical on): events sharing a `partitionkey` are
delivered in publish order, one at a time, to one consumer. It promises order per key, never
partitions: a Kafka adapter keeps it with the record key, a Pub/Sub adapter with the ordering
key, a Service Bus adapter with the session id. A broker that cannot order per key is
unsupported or reached through a workaround (`05_data_consistency_and_state_model.adoc` lists
both). The Kafka adapter keeps the promise as follows.

* **Producer.** `partitionkey` becomes the record key, so an aggregate's events hash to one
  partition. The producer is idempotent (`enable.idempotence=true`, which implies `acks=all`
  and bounds the in-flight requests per connection so that a retry cannot reorder a
  partition); `delivery.timeout.ms` bounds retries; `linger.ms` stays small, since the traffic
  is sparse and latency matters more than batching.
* **Consumer rule: lanes.** A partition is assigned to exactly one replica of a group, and
  the adapter runs the partition's records in per-key lanes (`agentic_eda/lanes.py`,
  taught in ch 4): one queue per record key drained by one task, so events sharing a key are
  handled one at a time in offset order, and keys are handled concurrently. A record with no
  key gets a lane of its own. Per-key order, one at a time, to one consumer follows from those
  two facts. Every turn of the delivery loop does three things, and none waits for another:
  fetch a batch, hand each record to its lane, commit what has finished. The commit is the
  watermark, per partition: the first offset still in flight, or one past the last fetched
  when none is, so a record is confirmed only once its handlers have returned and everything
  before it is confirmed too. After a crash everything from the watermark on comes back,
  finished or not, which is the at-least-once floor. `max_in_flight` (64 by default, on the
  adapter's constructor) caps the records handled at once across all keys: at the cap the
  loop pauses its partitions and keeps polling, so group membership never lapses during a
  long activation, and resumes them when a lane frees. On revocation the listener commits
  the watermark for the partitions being taken away and forgets them; a lane still running
  for one of them finishes unheard, and the store's version check (the fence, below) covers
  its write. `Lanes` and `Watermark` are broker-neutral: the Redis Streams adapter (ch 15)
  reuses them, and an adapter over a broker that serializes per key itself (Pub/Sub ordering
  keys, SQS FIFO groups, Service Bus sessions) needs neither. Consumer settings:
  `enable.auto.commit=false`; `auto.offset.reset` follows `start` (`latest` for `"now"`,
  `earliest` for `"beginning"`); session, heartbeat, and poll intervals at their defaults.
* **The fence.** A replica mid-activation when the broker reassigns its partition (a rebalance)
  can write after the new owner has moved on. A version check in the store is the fence: the
  `WorkflowStateStore` rejects a write whose expected aggregate version is stale, and the
  rejection returns to the handler as an error. One sentence in ch 8; never hit by the demos.
* **Head-of-line blocking** is per key only. A slow activation holds up the events behind it
  on its own key and nothing else; the partition count caps a component's replicas, not the
  activations one replica runs at once. A slow lane does hold the watermark back, so a crash
  replays the faster lanes' finished work along with it, and idempotency absorbs that.
* **Idempotency** stays the consumer's: deduplication by event id (the ch 6 projections, the
  ch 10 `IdempotencyStore`), because the contract is at-least-once and a redelivery arrives
  in order like any other event.

*Production notes* (named in ch 4 and ch 15, not built):

* **Confluent's Parallel Consumer** in key-ordering mode is the same lanes for Java, with one
  refinement the book's adapter does without: it records the offsets finished beyond the
  watermark in the commit's metadata, so a restart skips them instead of replaying them.
* **The partition count** is a deployment decision: it caps a component's useful replicas and
  is expensive to change once keys have hashed into it.
* **Share groups** (KIP-932, GA in Apache Kafka 4.2): many consumers per partition with
  per-record acknowledgement, order only within a fetched batch, no per-key order; the
  equivalent of Pub/Sub without ordering keys. They could back only a subscription mode that
  explicitly gives up order, never a silent adapter choice, and the Python clients do not
  support them for production. Not used; a sidebar candidate in ch 4 or ch 15.

== The Agent Activator

The activator wraps the port around one agent (`ch02_agent_activator`). Its handler signature
is the same under the pull loop and under a push endpoint, which is what makes the invocation
model an adapter concern. The activator owns five things.

* **The validating boundary.** Inbound: the envelope's schema, the UUID `id`, the required
  attributes, the data against the `@event` class bound to its type (below), which the agent
  receives as that class, with the event's attributes beside its data in `attributes_`, and
  never as an `WireEvent`, and from ch 13 the producer's identity; a rejected event
  is logged and, from ch 10, dead-lettered, and never reaches the handler. Outbound: the same
  contract on every publish, including the presence of `partitionkey` (from the ch 2
  practical).
* **How an agent is hosted, and how it states a fact.** The activator is a library, never a
  competing host, and the agent never learns that a broker exists. Its developer writes the
  agent as the framework's own documentation would have it, plus two declarations of
  `@event` classes, `consumes = eda.consumes(...)` and `produces = eda.produces(...)`, and
  one `attach` line on the app that hosts the agent; the activator does the rest. The two
  helpers have the same shape and check their classes the moment the module loads (that each
  carries `@event` and its `order_per`, and that what `produces` names survives the strict
  schema subset below), so a mistake fails at import. `produces` is also the schema the
  developer hands to the framework's typed-output line: with one class it returns that class
  itself, and wherever there is a choice, several classes or a class and `Nothing`, it
  returns a wrapper model holding their discriminated union under one field, because the
  OpenAI-family strict subset requires an object at the root and refuses a root-level
  `anyOf`. The developer never sees the difference; `output_schema=produces` works either
  way. An agent that may decide not to publish declares `produces(A, B, eda.Nothing)`:
  `Nothing` is a framework class with one field, `reason`, which the model returns as a
  positive answer and the activator logs and never publishes, so silence stays a failure
  for every agent (An activation that answers nothing, below). `produces()` with no classes
  declares a pure consumer, whose return value is ignored. Options are keyword arguments
  after the classes and name the classes they apply to (`consumes(ItineraryRequested,
  ItineraryApproved, interrupting=[ItineraryRequested])`, ch 7, the helper checking at
  import that the named classes are among the declared ones). No option exists on
  `produces` until a chapter needs one.
** *The catalog as code.* One Pydantic model per event payload in `travel_agency.events`,
   one module per context mirroring the catalog in `02_workflows_and_events.adoc`, each bound
   once to its type constant and to the field its order is kept within:
   `@event(ITINERARY_PROPOSED, order_per="trip_id")`, events sharing that field's value
   delivered in publish order, one at a time, and nothing promised across values. The two
   other forms are written out, never implied: `order_per=OWN_ID` on the event that starts
   a sequence (`booking.TripRequested`, keyed on its own id, which the events of the trip
   then share), and `order_per=None` on an event nothing orders
   (`system.DutyOfCareSweepDue`), published with a null key and handled in a lane of its
   own. A class that declares nothing is refused at `attach`, at startup, because an
   inherited or guessed key breaks order per key without a symptom. The function form,
   `event(TripRequest, ITINERARY_REQUESTED, order_per="trip_id")`, binds a class the
   developer does not own, so an existing agent's own models become the contract with no
   edit to the agent: it returns a subclass of that class with `EventContract` mixed in, and
   the agent still receives an instance of its own class. `contracts.data_of(fact)` is the one
   definition of what an event class puts on the wire (its own fields as JSON values,
   without its attributes or its type tag, and without an optional field left at its
   default, so a required field is always there, null included; the only default a
   contract may have is `None`, checked by `@event` at import through every class nested
   in the contract, so no stated value is ever missing from the wire), used by the activator on the way out and by a
   demo script publishing through the port.
   A field's meaning is part of the contract wherever its name and type leave a question
   open: a unit, the meaning of a null, an order, the owner of an identifier. It is written
   as `Field(description=...)`, and the class's purpose as its docstring, never as a `#`
   comment: Pydantic exports both into the JSON Schema (`description` on the property and
   on the object), and a comment is absent from it. A field with a name that settles its
   meaning has no description. The classes nested in an event class are described the same
   way.
   Every `@event` class subclasses `EventContract`, whose one field,
   `attributes_: SkipJsonSchema[ContextAttributes | None] = None`, carries the event's
   attributes in the same `ContextAttributes` class as the envelope's. The activator fills it
   on the way in with every attribute of the inbound event except `identitytoken`, since a
   credential never enters a model's context; `SkipJsonSchema` leaves it out of the schema a
   model answers against, so the model reads the attributes and is never asked to fill them;
   and the activator overwrites it on every publish. The trailing underscore keeps it clear
   of any payload field's name. A business fact the agent decides on still belongs in the
   data, because the attributes change under the agent (a relay sets `source` to the owner,
   and ch 14's Translator stands in front of a producer); the attributes inform the
   reasoning with who asked, when, and in which conversation. `WireEvent` is one occurrence on
   the wire, the envelope, and an `@event` class is the contract
   for a kind of event (`ch02_semantic_data_contracts` says so in one sentence). The binding
   adds an `event_type` literal to the class, which is what makes a union of event classes
   discriminated and what a model's answer names itself with. It is named `event_type` and
   not `type` so that it cannot collide with a payload field (a room's type, a fare's), and
   it never travels in the data, since the envelope carries the type. The attachment touches
   only the app's `router.lifespan_context`, so the framework needs no web framework of its own:
   the components bring FastAPI, and Starlette is a test dependency alone.
** *One activation.* For each inbound event the activator validates its data into the
   class bound to the event's type, with its attributes in `attributes_`, hands that
   instance to the framework adapter with the
   key (or the event id, when there is none) as the activation's thread or session id,
   reduces what comes back to zero or more instances of the classes in `produces` (an
   instance, a dict that validates as one, or JSON text parsed against `produces`, the
   wrapper unwrapped), rejects anything else at the boundary, and publishes each with its
   envelope: type and key from the binding, `id` and `time` generated, `correlationid` and
   `causationid` from the inbound event, `promptversion` and `modelversion` from
   configuration (ch 10). Returning from the activation acknowledges. Every outbound event
   passes through this one path, so the outbound boundary is one function. The activator
   sets the activation in a context variable before it invokes the agent, which asyncio
   carries into every task a framework spawns and into a worker thread, and that is how
   anything publishing from inside the activation, a publish tool or code, finds the inbound
   event, the source, and `produces` without being handed them.
** *An activation that answers nothing.* Because that one path is the only way out, the
   activator knows what an activation published, and silence is the failure an event-driven
   system has nobody waiting to notice: a model may answer in prose instead of calling a
   publish tool, or return an answer that is not a registered class, and nothing in a
   framework treats either as an error. So every activation of an agent with a non-empty
   `produces` must answer, and where none was published the activator raises: the event is
   never acknowledged, the broker redelivers it, and the activation runs again, which is the
   right treatment for a model that declined once in ten; repeated failure dead-letters in
   ch 10. An agent that may legitimately have nothing to say declares `eda.Nothing` among
   its `produces` and answers with it, reason included, as the Duty-of-Care Monitor's sweep
   does when no advisory affects a reserved destination: a positive answer, never silence,
   which is what keeps "decided nothing" apart from "drifted". Where code rather than a
   model answers (a plain function, a graph's final state), `None` or no produced instance
   maps to `Nothing` when it is declared, since code cannot drift the way a model can and
   the explicit form would be ceremony. Three nets, each at its
   own level: the validating boundary rejects a malformed answer, the activator catches a
   missing one, and ch 8's scheduler catches a fact that never reaches the component waiting
   for it. Taught with the publish tools in ch 7, where a model choosing not to call one is
   the case that makes it concrete.
** *Framework adapters*, one module each under `agentic_eda.activator`, selected by the
   agent object's class module (`langgraph`, `google.adk`, `crewai`, `llama_index`, or a
   plain coroutine function), so no framework is imported until it is matched and a
   component's image still carries only its own. The frameworks disagree on exactly two
   things, how an agent is invoked and how its answer is read out of the result, so an
   adapter is exactly two functions, `invoke(agent, request, thread_id)` and
   `extract_answer(result)`, and takes the agent as built (a compiled graph with whatever
   checkpointer it was compiled with, an ADK agent as constructed, a crew as assembled).
   Everything else is the core, written once.

| LangGraph

A framework the book does not cover is one more pair, and `attach(..., adapter=...)` names
one explicitly for an agent object whose class module matches nothing. A framework whose
invocation is synchronous runs in a worker thread, as CrewAI's own `kickoff_async` does, and
the activation holds its key's lane meanwhile like any other. The developer's one obligation is
that the agent answers with `produces`, which every framework's own typed-output feature
takes (`with_structured_output` or a graph's `output_schema`, ADK's `output_schema`, a task's
`output_pydantic`, LiteLLM's `response_format`, with `supports_response_schema` as the probe
for a model that cannot). The activator never supplies a schema to a prompt, and the
typed-output line is the only schema an LLM receives. The meaning of an inbound event's
fields is the developer's to give: `contracts.meanings_of(cls)` renders a contract's
docstrings and field descriptions as text, one line per class and per described field, read
from the same JSON Schema as any other reader's, and the Planner places it in its prompts
beside the request. Where a framework exposes that declaration, `attach`
compares it with `produces` at startup and fails loudly on a mismatch. The strict subset
also makes every property required, forbids extra properties, and does not enforce
`pattern`, `minLength`, `minimum` and their kin, so an optional field on an event class is a
union with `None`, and the activator validates every answer on receipt whatever the provider
promised.
** *One attachment, three positions.* The activator is a lifespan task on an ASGI app, and
   `eda.attach(app, agent, consumes=..., produces=...)` is the developer's one line, in the
   module that already defines the app; the compose file runs the app as the framework's
   documentation says. It opens the broker through `connect.event_broker` when the app
   starts and closes it when the app stops. A lifespan runs for the app a server serves and
   not for a sub-application mounted inside it, so `attach` goes on the app that is run, and
   the activator never starts silently otherwise. Where the framework has a self-hostable
   app, the activator attaches *inside* it and invokes through the host's own runner or
   runs API, so
   the host's sessions, tracing, UI, and persistence apply to event-triggered runs and
   nothing the host offers is lost: ADK's `get_fast_api_app`, LangGraph Server's custom app
   through `langgraph.json`'s `http.app`, Pydantic AI's AG-UI app. Where the framework has no
   host, the activator attaches inside *the component's own* FastAPI app, which is where the
   plain-Python agents live (the Front Desk is one already) and the CrewAI and LlamaIndex
   agents with them. Where the host is managed (LangGraph Cloud, CrewAI AMP), the activator
   runs *beside* it in a small app of its own and invokes over the host's API; named once in
   the book, never built. Push (ch 15) is a route on the same app in every position, the
   CloudEvents HTTP binding in and the same core behind it. ADK's own server offers the
   nearest alternative, `/apps/{app}/trigger/pubsub` and `/trigger/eventarc` routes that

   couple the agent's host to one cloud's delivery, where the attachment does not. The ch 7 Negotiator is the first
   attachment inside a framework's own app (ADK's); the ch 4 Front Desk and Inspiration crew
   attach inside their own apps. The ch 2 Planner runs in a FastAPI app of its own, the
   compiled graph invoked in-process and the activator's lanes governing concurrency. That
   is the shape most teams run LangGraph in production, the library inside their own
   service, with ch 8 swapping `InMemorySaver` for `PostgresSaver`. LangGraph Server, the
   commercial platform, takes the identical `attach` block in its custom app

   LangSmith key, runs the app's lifespan, runs the graph through the SDK on a thread, and
   keeps the thread's state. It is not in the book or the repository because the in-memory
   server announces itself as for development and testing only, its production form brings
   a Postgres, a Redis, and a license the book never shows, `langgraph-api` releases weekly,
   and runs go through the server's own queue, which takes concurrency out of the
   activator's hands. 2.8 says in one sentence that a team on the platform puts the same
   block in that app and what it trades.
** *Publish tools* (ch 7), for a turn that runs tools: `publish_tool(EventClass)` returns a
   plain async function named and documented from the class, whose parameters are its
   fields, flattened (the form every framework's tool wrapper reads natively, LangChain's
   `@tool`, ADK's automatic `FunctionTool`, CrewAI's `@tool`, LlamaIndex's
   `FunctionTool.from_defaults`, and the one ADK recommends over custom classes; ADK's own
   Eventarc toolset binds a `payload_schema` the same way), and whose body validates and
   publishes through the same path (the class is one of `produces`, and a tool's publish
   counts toward the answer the activation must give), returning the published event's id as
   the tool's result,
   which is the one thing an agent's loop is ever told about the broker and is there because
   a tool call must return something. The tool publishes when called, inside the turn, and
   the model may state several facts in one turn and read each id at once. It is the only
   reliable form for a tool-using ADK agent (`output_schema` beside tools in one request is
   supported by specific models only, with a fallback ADK's own documentation calls
   unreliable) and the natural one everywhere else, since stating a fact becomes one tool
   call. The Hotel Negotiator states `booking.RateNegotiated` this way from inside its A2A
   loop (ch 7, the book's first publish tool); the Recovery Agent states
   `servicing.CompensationDrafted` the same way (ch 9). The generic publish tool, a free
   `type`, `source`, or attribute for the model to fill, is the one thing ruled out, for the
   reason ADK's documentation gives: hallucinated destinations and malformed schemas.
** *`eda.publish(fact)`*, the code twin of the publish tool: callable from anywhere inside an
   activation, through the activation's context variable, and the same path (the class is
   one of `produces`, the answer is validated, the envelope is generated from the inbound event,
   the publish counts toward the activation's answer). It exists because a typed answer
   returned at the end cannot commit each of several facts before the next: the Booking
   Agent's reservation step (ch 7) publishes `FlightReserved` before it places the hotel
   hold, so a crash between the two loses nothing. Ch 7 introduces both twins together,
   `publish_tool` for a model and `eda.publish` for code. Agent code never receives
   `subscribe` or the broker connection, and the book's rule is that an agent publishes only
   through the activator: a raw publish would bypass validation, the envelope, the answer
   accounting, and from ch 10 and ch 13 the version stamps and the identity token. Demo
   scripts and tests, which are not agents, keep the port.
+
Neither the typed answer nor a publish tool restricts when a fact is stated: an
orchestrating agent states facts as its workflow advances, mid-activation, and the test for
each fact is the boundary test of `ch02_agentic_boundaries`, never timing. What both share
is at-least-once. A fact stated mid-activation is out, and if the activation dies afterwards
and its inbound event is redelivered, the rerun states it again under a new id, which no
consumer can deduplicate. A durable agent resumes from its checkpoint past the fact (ch 8);
until then the design's agents state their facts at the end of the activation (the Planner's
typed answer, the classifier's one request, the Negotiator's one `RateNegotiated` at the end
of its loop, made durable in ch 8), and the Booking Agent's steps are deterministic code
whose activation returns the facts it commits. To confirm in code before ch 2: that
`ainvoke` on a compiled graph accepts the request under a field found by type, and that the
wrapper `produces` returns for several classes is accepted as
`response_format` by the readers' four model choices; before ch 7: that a lifespan task in ADK's app can obtain
a `Runner` on the app's session service, and that ADK accepts the flattened function with
Pydantic-typed fields (dates, enums, nested items).
* **One key at a time.** The activator handles the events of one key sequentially and
  acknowledges each by returning; the adapter runs keys concurrently in lanes and commits by
  watermark. Deferral to the next activation is the default for anything that arrives on the
  key while a handler runs.
* **The activation inbox** (ch 7). An activation can run for minutes, and a relevant fact can
  land meanwhile. The delivery loop never stops fetching, so a record for the key under
  activation waits in that key's lane; a record of a type declared interrupting by the
  subscription is not left there behind the handler: the running activation takes it from the
  lane's pending queue between reasoning steps, as an observation, and revises its beliefs
  rather than finishing on stale ones. Activator and adapter share one process and one event
  loop, so this is a peek into the lane, not a second consumer. Per-key ordering makes this safe, because only the
  running activation can see that key's events; the interrupting events' offsets are
  committed with the activation's when it returns. Which types interrupt which activations is
  declared on the agent's `consumes` (`interrupting=[...]`, naming classes among the declared
  ones), never inferred by the model, and the port surface is unchanged. An interrupting type arriving when no activation holds its key is handled as an
  ordinary event in its own activation. The Planner declares its own request type,
  `planning.ItineraryRequested`, as interrupting for its planning activations: a newer request
  for the trip under activation supersedes the run in progress, which is abandoned, answered
  with `planning.ItineraryRequestSuperseded`, and restarted from its checkpoint with the new
  requirements. Nothing else declares anything in the book.
* **No defer, no nack.** The port offers neither, and the activator adds neither. Staging an
  event until its prerequisite arrives is the `InboxStore` (the Agentic Inbox, ch 4):
  activation gated on the completeness of its context, verified deterministically before any
  inference runs. Re-sequencing at ingress happens exactly once in the design, at one line,
  inside the Semantic Router: the time window of ch 4's semantic windowing is sorted by the
  sender's timestamp before the one bulk call, a deterministic fix that works only where a
  trusted sequence exists. Bouncing an event through a consumer that runs a model would re-run
  the model, and a nack fights per-key ordering everywhere (block the key, as queue brokers do,
  or break the order, as a retry topic does), so NACK and retry is analyzed in the book and not
  built.

== Producer Identity (ch 13)

An application-layer identity, portable across brokers:

* Every component holds its own key pair, generated at build time; the public keys are a
  committed registry in the application's package (`travel_agency/identity/`), its path
  handed to the framework's verifier by a setting, for the compose stack and a secret store
  in ch 15.
* On publish, the activator adds `identitytoken`: a compact signed token (JWS) whose subject is
  the component's `source` and whose claims bind the event's `id` and `type`, so a token copied
  from one event does not verify on another.
* On consumption, the validating boundary verifies the signature against the registry, checks
  that the subject equals the event's `source`, that the bound id and type match, and that the
  source is an allowed producer of the type (the catalog's owning context in
  `02_workflows_and_events.adoc`; for an open-host request type, any registered caller of that
  published language). The Guardrail Worker performs the same check on sensitive
  topics before republishing to the trusted topic. A failure is a rejection at the boundary,
  logged and dead-lettered, and never a handler call.
* A relay (`EventScheduler`, outbox relay) publishes an event built and signed by the owner at
  scheduling or enqueue time, verbatim; the relay adds nothing and holds no key of its own.
* Kafka principals with topic write ACLs in the compose stack are defense in depth and the
  enforcement view of the single writer promised in ch 2.2: a component can write only its
  own context's topic.
* Before ch 13 the attribute is absent and the boundary does not require it; the attribute and
  its verification arrive together. Ch 13's red-team script publishes a forged
  `booking.TripConfirmed` and watches it rejected.

== The Replay Script

`python -m agentic_eda.replay <recording.jsonl>` republishes a recording through the port.
The recording format is the audit consumer's: one CloudEvent per line, structured JSON. The
script preserves every attribute and `data` exactly, so keys,
correlation, causation, and identity survive; publishes in file order; paces publishes by the
recorded `time` gaps unless `--fast`; and filters by `--correlationid` or `--type` when asked.
It runs against a fresh stack, since idempotent consumers skip already-seen ids.
Uses: the optional shortcut for ch 7's first Paris run (the recording ships in
`chapters/ch07/data/`), and ch 12's offline harness, which replays the same recording into the
`InMemoryBroker`. DLQ replay (ch 10) is broker behavior and a different script: it selects
parked events on `dlq.<context>` by `--type` and by the `--promptversion` that produced them,
and republishes them with their keys, so the Planner on the fixed prompt answers them in order.

== Prompts as Configuration

A component is never edited after its first chapter (01_system_overview.adoc, ground rules),
and a prompt is the part of an agent most likely to change, so prompts are configuration, not
code. Every prompt is a versioned file inside the component's package
(`<package>/prompts/<name>.v<N>.md`), beside the module loading it (`prompts/__init__.py`)
through `importlib.resources`, never through a path built from `__file__`. The files are
therefore installed with the package and found the same way from the source tree and from
the installed copy, and an image holds every version. The component's suite renders each
prompt file with the agent's own variables from the installed package, so a file left out of
the package and a variable missing from a file both fail the gate. The
compose file selects the version by environment (`PROMPT_VERSION`), and the activator stamps
`promptversion` and `modelversion` on every event the agent publishes. Ch 10's prompt regression
selects a faulty version and replays the dead-lettered events after a bump; ch 12's optimality
regression replays recorded requests through a new version. A component's typed-output
classes have field descriptions like the event classes (The Agent Activator, the catalog as
code), and those descriptions are sent to the LLM with every call, inside the schema. The
division is fixed: a description defines a field (what it is, its unit, the meaning of a
null) and the prompt file instructs (how to decide). Descriptions are code and are fixed with
the component, so a change of behaviour is always a new prompt version. A behaviour switch a
later chapter enables (the reservation step, the barrier wait, the policy wait) is the same kind of
configuration, a flag read by the component at start, off by default, and absent from every
compose and configuration file until the chapter that switches it on. A flag is the default
mechanism; a new version of the component (`<name>_v2`, selected by compose) is used only where
the added behaviour cannot be segregated cleanly behind a flag inside one version. A port
present and switched off is the same kind of setting: the Planner's hydration adapter is
`HYDRATION_ADAPTER` (default `none`, an adapter that loads nothing) and its A2A client is
`RESEARCH_AGENT_URL` (unset by default, meaning off), each read at start, switched on by the
compose file of the chapter that teaches it, and mentioned by no earlier chapter's compose
file, configuration file, or prose.

== Repository Layout Conventions

* `lib/agentic_eda/` and `lib/travel_agency/`: the framework and the application's shared
  code (Two Packages, above), each a directory with its own pyproject, its package, and its
  tests. Every component installs both, the framework first
  (`pip install ./lib/agentic_eda ./lib/travel_agency`), and `travel-agency` declares its
  dependency on `agentic-eda` at the exact version in the tree.
* `components/<book_component_name>/`: one self-contained directory per component, named
  after the book's component (e.g. `itinerary_planner_minimal`, `audit_consumer`,
  `airline_reservation_system_sim`): sources, Dockerfile, pyproject with **pinned exact
  versions**, unit tests. A component's image carries only its own dependencies; one
  framework's agent never drags another's.
* `starter/`: the smallest application on the framework, for a reader starting their own
  (Two Packages, above): its own package, Dockerfile, pyproject, compose file, test, and
  README, with no import of `travel_agency`.
* `chapters/chNN/`: the chapter's README (what is demonstrated, how to run it), its
  `compose.yaml` entry point, its demo scripts, its recordings under `data/`, chapter-level
  tests, and `test.sh`. Shell blocks in READMEs contain commands only, no `#` comments,
  because zsh, the macOS default shell, rejects them when a block is pasted interactively.
  Each block is introduced by a prose sentence saying what the commands do, and how long they
  take when that is not obvious (first builds, model downloads). Documented compose commands
  always carry `--build`: Compose never checks the source tree on a plain `up`, while
  BuildKit's layer cache makes an unchanged rebuild cost seconds, so readers who edit code
  never chase stale images. Chapter walkthroughs lead the reader step by step and never leave
  them guessing, in a fixed two-terminal model: the first terminal starts the stack and runs
  one persistent `docker compose logs -f <services>` naming every demo participant (Compose
  attaches containers created later, so the command never needs restarting); the second
  terminal runs every action: demo triggers (`up -d --build --force-recreate
  <script-service>`), kills, new consumers. Each act gives the second-terminal commands, then
  an "Observe" that says which component prints what in the watch stream and what it proves.
  Demo scripts narrate events, not model output: every publish and receive is printed as an
  event card via `agentic_eda.console` (id, type, source, the other attributes, data), with long
  values truncated; the full facts are on the audit record. The ch 1 minimal Planner holds
  every reply until the 45-second mark (`PLANNING_SECONDS`; the chapter's stated inference
  time), so the durability act's kill window does not depend on the reader's model speed.
  Components get the same narration for free: the Kafka adapter logs a card for every event
  published or received (the `EventBroker` logger, INFO), so `docker compose logs <component>`
  shows that component's side of the conversation.
* `compose/`: one fragment **per infrastructure service** (`kafka.yaml`, `ollama.yaml`;
  later `postgres.yaml`, `minio.yaml`, and so on). A chapter's `compose.yaml` uses `include:`
  to pull exactly the needed fragments, so no chapter drags unused infrastructure. The compose
  file is the only thing that differs between chapters: which components it selects (ch 2
  selects the LangGraph Planner in place of ch 1's), which adapter each port gets (in-memory
  or Postgres), which prompt version, and which behaviour flags are on. Ch 4's compose scales
  the Semantic Router to two replicas (`deploy.replicas: 2`), the book's demonstration of
  competing consumption and per-key serialization.
* `docker/`: shared Dockerfiles, named by what they build: `python.Dockerfile`, the Python
  image with both libraries, used by demo scripts, the replay script, the application
  library's suite, and chapter-level tests; and `agentic_eda.Dockerfile`, the image with the
  framework alone, used by the framework's suite.
* `.env` at the repository root: one required file of reader configuration for the whole
  book. Containers read it through `env_file`; compose-time switches (`OLLAMA_ENABLED`)
  reach the shared fragments through `include:` with `env_file`, since Compose interpolation
  only reads the project directory's own `.env`.
* Tests: unit tests are colocated with each component and run inside that component's image
  (the only environment with its exact dependencies). The entry point is per chapter:
  `tests-<component>` services plus `tests-chapter` in the chapter's own
  `compose.tests.yaml`, looped by the chapter's `test.sh`, the CI gate. Tests have a
  separate compose file deliberately: they must run with no Kafka, no model, and no `.env`.
  A component's own suite tests its side of a conversation against a stand-in (the Planner's
  clients against recorded supplier replies, a simulator through a test client). Where two
  components meet over a protocol, one more suite in the chapter's directory runs the
  caller's image against the running callee: from ch 2, `tests-planner-with-suppliers` runs
  the Planner's clients, and the whole graph with a scripted model, against both simulators.
  Its tests are located in `chapters/chNN/supplier_tests/`, apart from `tests/`, because they
  need the caller's image and the chapter's own tests need only the two libraries'.
* Simulators: a simulator stores nothing it can generate. Its offers come from the world
  seed and a generator seeded by the question asked (`world.dice`), so the same question
  gets the same answer on every run and every machine; only what a caller creates (an offer
  made, an order held) is kept, in memory. Every simulator prices in US dollars and keeps
  time in UTC, so no component converts a currency or a time zone. A simulator's behaviour
  switches are settings read at start with an off default (`RESPONSE_DELAY_SECONDS=0` on the
  airline, its slow-vendor mode), switched on by the compose file of the chapter that needs
  them. A simulator's image carries a `HEALTHCHECK` on its port, so a compose file waits for
  it with `service_healthy`. A caller reaches a supplier at an address read from a setting
  (on the Planner, `AIRLINE_URL` and `HOTEL_INVENTORY_URL`), set by the chapter's compose
  file; unset, the client raises an error naming the setting. The caller's client translates: it asks in the supplier's terms
  and answers in the caller's own, so no supplier field name reaches an agent's code.

== House Style

* **asyncio throughout.** Agents are async loops; handlers are async callables.
* **Everything runs in containers.** The reader needs git, Docker (with Compose), and an
  internet connection; every reader command is `docker compose ...` from the chapter
  directory, identical on Mac, Windows, and Linux. Host Python is a contributor
  convenience, never a requirement.
* **Model access:** LiteLLM; the general-case model, used by most agents, is the
  `LLM_MODEL` string in `.env`, one of four reader choices: Gemini (default), OpenAI,
  Claude, or Ollama. Each choice is one block to uncomment, key included; the Ollama
  block needs no key and carries `OLLAMA_ENABLED=1`, which replicas-gates the service.
  The service pulls its own models on first start, and consumers attach with
  `depends_on ... required: false`; no compose flags and no manual pulls exist anywhere.
  The four blocks are curated defaults, not a boundary: no compose file or component
  enumerates providers (containers receive the whole `.env`, agents read only
  `LLM_MODEL`), so any of LiteLLM's 100+ providers is two `.env` lines, its key
  variable plus the model string, and providers unknown to LiteLLM are still reachable when
  OpenAI-compatible, via `openai/<model>` + `OPENAI_API_BASE`.
  Ollama placement: `compose/ollama.yaml` defines two flavors of one service off a
  shared anchor, `ollama` (CPU, `OLLAMA_ENABLED=1`) and `ollama-gpu` (NVIDIA device
  reservation, `OLLAMA_GPU=1`), the GPU flavor network-aliased to `ollama` so the
  address is `http://ollama:11434` either way and switching flavors is one `.env`
  change, never a file copy. The reservation lives only on the gated service because it
  fails startup outright on machines without an NVIDIA runtime. Neither flavor
  publishes a host port, so a natively installed Ollama never collides. macOS never
  exposes Apple GPUs to containers, so `.env.example` also documents the host-native
  variant (`OLLAMA_API_BASE=http://host.docker.internal:11434`; GPU via Metal, no
  container), and LLM-calling services carry
  `extra_hosts: host.docker.internal:host-gateway` so that variant works on Linux too.
  Reader-facing setup for all three variants lives in one place: the root README's
  "Local models with Ollama" section; chapter READMEs and `.env.example` point there.
  Predictive throttling against provider limits (ch 11) is LiteLLM's rate-limit
  configuration, tokens and requests per minute per deployment, never hand-written.
* **Chapter-mandated local models** (the ch 4 Semantic Router's embeddings, ch 13's
  Llama Guard, the ch 11 fallback chain) never read the general `LLM_MODEL`. The chapter
  pins the component's model in its own compose files and forces the service on by
  including `compose/ollama.yaml` with an env-file list,
  `env_file: [../../.env, ollama-required.env]`, where the committed second file
  overrides `OLLAMA_ENABLED=1` and lists the `OLLAMA_MODELS` to pull. A chapter never
  edits reader configuration.
* **Comments clarify.** All code is read and judged by humans; comments explain what the
  code cannot say itself, and listings printed in the book are extracts of this working
