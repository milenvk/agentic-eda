== Purpose and Ground Rules

This document is the upfront, whole-application design for the book's running project. The book
introduces the system chapter by chapter, but the author needs the destination fixed in advance so
that every chapter's addition lands in a coherent final architecture. The design obeys these
decisions, settled in the design interviews of 2026-08-09:

* **The outline is the complexity budget.** A component exists only if a chapter's practical
  implementation needs it to teach its pattern. The book serves pedagogy for a 300–400 page
  journey, not an industry-complete enterprise application.
* **Business model:** a digital-first B2C travel agency that lands a corporate (B2B) client
  mid-book, as Chapter 8 already implies.
* **Research-grounded texture:** the business realism from the author's travel-industry
  research (NDC offers, fare conditions, mid/back-office operations) survives as naming, seeded
  data, and sidebar material — never as components the reader must hold in their head. See
  "Realism kept as texture" below.
* **Realism split:** agents only where non-deterministic reasoning is genuinely needed; deterministic
  work is done by deterministic code and simulated vendor services.
* **Front door:** a minimal web/chat UI exists as a demo shell (kept out of the book's page
  budget); runnable scripts remain the primary teaching harness. Every entry into the *system*
  is a published event — the UI, the email replay, and the scripts are all edge producers. A
  framework's own UI (ADK's `adk web`, used to develop the Planner) is an entry into a single
  agent, never into the system.
* **LLM strategy:** reasoning agents default to one cloud API key; Ollama is the documented
  zero-cost fallback and powers the Semantic Router and Guardrail models. Model access goes
  through **LiteLLM** rather than a hand-written port (see Ports below).
* **Vendors:** external systems are shipped, deterministic, seeded simulators.
* **Frameworks:** the roster is fixed by section 1.5 — **LangGraph, Google ADK, LlamaIndex,
  CrewAI**. Framework agents are the showcases; every other agent is plain Python against
  the Ports.
* **Repo model:** the code — and these design docs — are in this repository, separate from
  the book manuscript, on a single `main` branch. Each component is a self-contained
  directory (sources, Dockerfile, dependencies, unit tests); each chapter owns
  `chapters/chNN/` — a README, the chapter's Docker Compose files, and its demo scripts —
  composing exactly that chapter's cast from the shared component pool. The whole book's
  code is visible at a glance and a fix lands exactly once. `main` is tagged at each
  chapter's manuscript freeze (`chNN-1.0`, re-tagged after errata) with a release per tag,
  so the tree as printed stays reachable.
* **Additive evolution:** a chapter extends an existing component or replaces it with a new
  one subscribed to the same events — it never rewrites a component in place, and a
  superseded component stays in the tree as its chapter's artifact (each chapter's compose
  files select which components run). Every chapter's teaching code is therefore present in
  the one shared tree. Where a later in-place extension would change behavior an earlier
  chapter's demo depends on, the component is replaced rather than extended, decided at
  chapter planning.

== The Business

The agency sells trips: flights, hotels, rental cars, and multi-city itineraries. Customers reach
it through a chat UI and by email. Suppliers are reached through a booking supplier API and a
payment provider. Narratively the operation still has a front office (intake, planning, booking),
a mid office (policy checks, human approvals), and a back office (audit trail, memory) — but that
framing is one paragraph of story, not a population target.

The business evolves in four phases that track the book's parts:

[cols="1,2,3", options="header"]
|===
| Phase | Book part | Business capability added

| Consumer booking core
| Part 1 (ch 1–6)
| Take a trip request, plan it, book it, support the customer, remember everything that
  happened.

| Richer products + first B2B client
| Part 2 (ch 7–9)
| Multi-city trips searched in parallel; a corporate client with travel policies and manager
  approvals; disruption handling with real compensation.

| Operational hardening
| Part 3 (ch 10–13)
| Payments that survive retries, cost governance, testing, security.

| Production
| Part 4 (ch 14–15)
| Observability, schema evolution, and migration to managed cloud services.
|===

=== Domain Map

Decided in the design pass of 2026-08-24. The business divides into eight subdomains, each held
one-to-one with a bounded context and an event prefix, so prefix, context, and subdomain are one
name. The one-to-one hold is a deliberate simplification: where DDD would split a subdomain into
several contexts (a language that diverges inside it, or an external system's own model), this
design answers with aggregates inside one context and with edge adapters at the vendor's boundary.

[cols="2,1,4,3", options="header"]
|===
| Subdomain | Prefix | Language and facts | Components

| Trip Planning
| `itinerary`
| request, preferences, availability, offers, fare conditions, proposal, assembly, arbitration;
  ItineraryProposed, ItineraryAssembled, FlightSearchRequested, HotelSearchRequested,
  FlightOffersProposed, HotelOffersProposed, ActionProposed, ActionCommitted
| Itinerary Planner, Destination Research Agent, Trip Coordinator (fan-out and barrier),
  Airline and Hotel Agents (offers), Arbiter

| Booking
| `booking`
| trip request, itinerary approval, reservation, confirmation, cancellation, car class,
  follow-up; TripRequested, ItineraryApproved, TripConfirmed, TripCancelled, FlightBooked,
  HotelBooked, CarRentalReserved, CarRentalUnavailable, CustomerFollowUpDue; two aggregates: the customer request (Booking Agent)
  and the trip order (the Coordinator's `WorkflowStateStore`)
| Booking Agent (the demo script stands in during ch 1), Trip Coordinator (order lifecycle and
  booking step), Rental Car Agent

| Payment
| `payment`
| charge, authorization, idempotency key; PaymentRequested, PaymentAuthorized; kept separate
  for idempotency against a real side effect (ch 10) and data segregation (ch 13)
| Coordinator's payment step, Payment sim

| Corporate Travel Policy
| `policy`
| policy, violation, approval, manager, escalation, timeout; PolicyViolationDetected,
  ApprovalRequested, ApprovalGranted, ApprovalRejected, ApprovalTimedOut
| Policy Gate, approval console, Coordinator's waiting state

| Disruption and Care
| `disruption`
| disruption, sold out, compensation, rebooking, advisory, risk; HotelSoldOut,
  CancellationDrafted, FlightBookingCancelled, TravelRiskDetected
| Cleanup Agent, compensation code, Duty-of-Care Monitor, Hotel Agent (rebooking negotiation)

| Customer Support
| `support`
| ticket, resolution; SupportRequested, SupportTicketResolved; a bought capability whose
  vendor model stops at the edge adapter
| Support Desk AaaS sim behind its adapter

| Customer Communication
| `communication`
| email, message, channel, classification, triage; EmailReceived, VendorUpdateReceived,
  TripRequestReceived (provisional name, settled at ch 4 planning)
| email replay script, Semantic Router

| Destination Knowledge
| `content`
| brochure, document, index, claim reference; BrochureUploaded, DocumentAvailable
| claim-check ingestion, Destination Research Agent
|===

The map's rules:

* **A component is placed by the facts under its ownership, not by its subject.** The Airline and Hotel
  Agents own planning facts (offers, proposals) and book nothing, so they sit in Trip Planning;
  the Coordinator's booking step owns `FlightBooked` and `HotelBooked`; the Rental Car Agent
  owns `CarRentalReserved` and does no planning, so it sits in Booking. That asymmetry is the
  ch 7 choreography demonstration (a car added by reacting to `FlightBooked`, with nobody
  orchestrating it), not a modeling accident.
* **One owning context per event type.** Several components may publish a type when they stand
  in the same context (the demo script and the Booking Agent for `TripRequested`); a component
  in another context that republishes an inbound fact publishes its own type (the Router's
  `TripRequestReceived`, turned into `TripRequested` by the Booking Agent).
* **`system` is the platform's technical namespace, outside the map.** BudgetExceeded,
  ModelFallbackActivated, EventQuarantined, and DutyOfCareSweepDue are technical events in
  ch 1's sense, facts about the system's own behavior, each owned by the mechanism that emits it.
* **Scheduled events carry the prefix of the asserted fact.** ApprovalTimedOut is `policy`
  though the scheduler fires it; a wake with no business meaning (DutyOfCareSweepDue) is
  `system`.

=== Identifiers

Identity conventions, in the book's order of introduction:

* **Event `id`** (CloudEvents core attribute) — every event's own identity, minted as a
  UUID and **globally unique across the entire solution** by architectural decision. This is
  deliberately stricter than the CloudEvents minimum (unique per `source`): the reader's own
  system may not have a `source`, and a single unique key keeps references and table lookups
  one-column simple. The book explains this reasoning where CloudEvents is introduced
  (ch 2.5).
* **Causation** — a reply carries the globally unique id of its request: ch 1's
  `ItineraryProposed` holds the `TripRequested` id as a `request_id` payload field, and the
  demo script matches on it. Ch 2.6 promotes it to a `causationid` extension attribute
  (settled at ch 2 planning: one attribute, since ids are globally unique); ch 14's
  `traceparent` carries parent identity for observability, not business causation.
* **`correlation_id`** — the execution-thread key (established in ch 2.6), minted at the
  first request and copied to every event of the execution; it replaces the synchronous
  call stack. Causation is a link, correlation a label: following causation walks the
  thread hop by hop, filtering on correlation returns it whole.
* **`context_path`** (from ch 7.6) — hierarchical context scoping, e.g.
  `/trips/{correlation_id}/paris/hotel`.
* **Order id** — a business fact, not a scoping mechanism: created and returned to the
  customer only when an order comes into existence (the booking chapters, ch 7–8), expected
  as a CloudEvents extension attribute; the minting owner and its exact relationship to
  `correlation_id` are decided at that chapter's planning. Scoping stays correlation's job —
  sub-workflows may run before any order exists or never concern one. There is still no
  order aggregate or Order Service: the trip *is* the correlated event stream, read through
  semantic views (ch 6) and workflow state (ch 8).

=== Realism rule: what is an agent and what is not

Agents exist only where non-deterministic reasoning is genuinely needed; deterministic work is done
by deterministic code and simulated vendor services. Chapter 1's request-response scenario and
its cascade figure use six design-true components — Booking Agent, Itinerary Planner Agent,
Airline Agent, Hotel Agent, and the airlines' and hotels' independent booking systems — so
deterministic vendors are present from the first chapter and the reader's mental picture of the
cast never changes as the book progresses; the connection-explosion figures stay deliberately
generic.

=== Realism kept as texture

The researched industry realism stays in the book as prose, not code:

* **NDC offers and fare conditions** — the Airline Booking System sim's flight offers carry
  change/refund-penalty fields the airline and hotel agents reason over; a sidebar can name NDC
  as the real-world shape.
* **IATA ONE Order** — a sidebar candidate where event sourcing is taught (ch 6): the industry
  is converging on exactly the "single record of the trip" the event log provides.
* **Treasury, VCCs, ticketing deadlines, commission reconciliation** — mid/back
  office operations the prose can gesture at (e.g., in ch 1.4's scenarios or a ch 8/ch 9
  sidebar) as further applications of the same patterns, without building them.

=== Ports and infrastructure

Ports (all outline-established, unchanged): `EventBroker`, `EventScheduler`,
`WorkflowStateStore`, `SemanticViewStore`, `BlobStore`, `InboxStore`, `BarrierStore`,
`IdempotencyStore`. The low-level design — exact port signatures, the event envelope,
minting rules, naming, and repo layout conventions — is `04_implementation_design.adoc`.

**`EventBroker` subscription capabilities.** Beyond per-event-type subscription, the port
offers subscribe-all (or an event-type prefix) — the intersection floor across backends,
never arbitrary regex. The Kafka adapter implements it with a regex topic subscription over
the application's namespace, picking up newly created topics on the periodic metadata
refresh; an adapter whose backend has no native patterns emulates the promise from its own
event-type→topic registry; on GCP (ch 15) the mechanism moves into infrastructure — an
Eventarc Advanced enrollment feeds a pipeline that pushes to the consumer's ingestion
endpoint, so the consumer does not subscribe at all. Consumers therefore come in both
invocation models the container supports (ch 2.4): a pull loop, or a push endpoint the
infrastructure delivers into. The audit consumer is the standing beneficiary: it sees every
event, including types added chapters later, with no code change.

**Model access — LiteLLM, not a Port.** There is deliberately no hand-written model port.
The book's Ports exist to abstract infrastructure the architecture owns; model access is
already commoditized by **LiteLLM**, a mature library exposing 100+ providers (cloud APIs and
Ollama alike) behind one interface, with fallbacks, retries, and cost tracking built in. Writing a
port over it would model exactly the anti-pattern the book warns against — abstracting an
abstraction. Concretely:

* **Plain-Python agents** call the LiteLLM SDK directly; the model is a config string
  (`gemini/...`, `anthropic/...`, `ollama_chat/...`), and the cloud-key-default /
  Ollama-fallback strategy is a LiteLLM `fallbacks` configuration rather than code.
* **ADK agents** use ADK's own `LiteLlm` wrapper (`Agent(model=LiteLlm(model=...))`) — the
  framework's native model abstraction *is* LiteLLM, which is the precedent for this decision.
* **LlamaIndex, LangGraph, and CrewAI agents** either use their LiteLLM integrations or
  point their OpenAI-compatible client at a LiteLLM endpoint — CrewAI's own LLM class is built
  on LiteLLM — so either way the model choice stays in config.
* **Chapter 11** divides cleanly: mechanical provider fallback on outage is LiteLLM
  configuration; the *economic circuit breaker* (token budget per `correlation_id`, spanning
  agents and frameworks) remains the book's own pattern on the `WorkflowStateStore`, because no
  gateway can know workflow identity across a polyglot swarm.
* **Chapter 15**'s swap to Vertex AI / Bedrock becomes a one-line model-string change — a
  cleaner zero-lock-in proof than a custom adapter.

Infrastructure: Kafka (KRaft, single container) + Kafka Connect HTTP sink for push, PostgreSQL,
MinIO, Redis (alternative broker adapter), Ollama, LiteLLM (SDK in-process), APScheduler relay
process, OTel + Jaeger, Docker Compose (each chapter branch's compose file *is* that chapter's
stack; profiles only for optional pieces like the UI shell), Terraform (ch 15).
