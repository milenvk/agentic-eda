== Purpose and Ground Rules

This document is the upfront, whole-application design for the book's running project. The book
introduces the system chapter by chapter, but the author needs the destination fixed in advance so
that every chapter's addition lands in a coherent final architecture. The design obeys these
decisions, settled in the design interviews of 2026-08-09, the convergence of 2026-09-05, and the
reconciliation of 2026-09-11:

* **The outline is the complexity budget.** A component exists only if a chapter's practical
  implementation needs it to teach its pattern. The book serves pedagogy for a 300 to 400 page
  journey, not an industry-complete enterprise application. A use case stays whenever it is the
  only one that demonstrates a pattern well; the number of subdomains is not a target.
* **Business model:** a digital-first B2C travel agency that lands a corporate (B2B) client
  mid-book, as Chapter 8 already implies.
* **Research-grounded realism:** the industry's standards give the model its nouns and the
  simulators their shape, in four rules. The agency's language uses the industry's entities and
  relationships (the glossary beneath the domain map). The simulators expose supplier surfaces
  shaped like the real ones in a printable subset, endpoints and field names, never schemas.
  Payloads borrow the industry's names and codes inside the book's own Pydantic models. A
  standard is named in prose only where it explains a design choice. See "Realism kept as
  texture" below.
* **Realism split:** agents only where non-deterministic reasoning is genuinely needed;
  deterministic work is done by deterministic code and simulated vendor services.
* **Front door:** every entry into the *system* is a published event. The Front Desk is the
  Customer Relations context's agent (ch 4): a small FastAPI app whose chat UI is a demo shell
  kept out of the book's page budget, and whose intent classifier and publishing code are in
  it. It is the writer of that context's two aggregates, the Customer and the Conversation. It
  identifies the customer, keeps the session, records `customer.ChatMessageReceived` when the
  customer writes, classifies the message and writes the serving context's request
  (`booking.TripRequested`, `booking.CustomerReplied`, `support.SupportRequested`,
  `destination.InspirationRequested`), follows the customer's trips by trip id, and records
  `customer.CustomerNotified` when it delivers a message, so the audit trail records what the
  customer was told. Until ch 4 the demo scripts hold the customer's seat and write the same
  requests; the email replay and the Router hold it for email. A framework's own UI is an entry
  into a single agent, never into the system.
* **LLM strategy:** reasoning agents default to one cloud API key; Ollama is the documented
  zero-cost fallback and powers the Semantic Router and Guardrail models. Model access goes
  through **LiteLLM** rather than a hand-written port (see Ports below).
* **Vendors:** external systems are shipped, deterministic, seeded simulators, each shaped like the
  real supplier surface behind it.
* **Frameworks:** the roster is fixed by section 1.5: **LangGraph, Google ADK, LlamaIndex,
  CrewAI**. Framework agents are the showcases; every other agent is plain Python against
  the Ports. Debut order: LangGraph in ch 2 (the Planner), LlamaIndex in ch 3 (the Research
  Agent), CrewAI in ch 4 (the Destination Inspiration crew), ADK in ch 7 (the Hotel Negotiator)
  and again in ch 9 (the Recovery Agent).
* **Repo model:** the code, and these design docs, are in this repository, separate from
  the book manuscript, on a single `main` branch. Each component is a self-contained
  directory (sources, Dockerfile, dependencies, unit tests); each chapter owns
  `chapters/chNN/`, a README, the chapter's Docker Compose files, and its demo scripts,
  composing exactly that chapter's cast from the shared component pool. The whole book's
  code is visible at a glance and a fix lands exactly once. `main` is tagged at each
  chapter's manuscript freeze (`chNN-1.0`, re-tagged after errata) with a release per tag,
  so the tree as printed stays reachable.
* **Immutable components; a chapter is its compose file.** A component is written in its
  final form when it first appears and is never edited afterwards. Behaviour a later chapter
  teaches is present from the start and switched off by configuration until that chapter's
  compose file switches it on: the Booking Agent's reservation, compensation, and payment
  steps exist in ch 3's code and are enabled in ch 7, 9, and 10; a port's adapter is chosen by
  configuration (the trip store is in-memory in ch 3 and Postgres from ch 8, both adapters
  present from ch 3). A chapter differs from the one before only in its compose file: the
  infrastructure fragments it includes, the components it selects, and the configuration it
  applies. Every behaviour flag defaults to off, so a chapter's compose and configuration
  files mention only what that chapter switches on and an early chapter's files never name a
  later chapter's feature. A new version of a component (`<name>_v2` beside `<name>_v1`,
  selected by compose, the superseded one staying in the tree as its chapter's artifact) is
  the exception, used only where the added behaviour cannot be segregated cleanly behind a
  flag inside one version; the LangGraph Planner selected in ch 2 in place of ch 1's plain one
  is the one planned case. New workflows arrive as new components; a new agent that duplicates
  an existing one with different sub-agents is avoided. Prompts and agent configuration are
  not code: every prompt is a versioned file the compose file selects, and the container
  stamps its version on every event. Two consequences: the design is complete before the first
  component is written, and a component is finished before its chapter's prose is written,
  since the prose describes code that exists. The prose introduces a component progressively,
  showing the part its chapter's pattern needs; the code does not wait for it.

== The Business

The agency sells trips composed of supplier products: flights, hotel stays, rental cars, and
multi-city itineraries. Customers reach it through a chat UI and by email. Suppliers are reached
through their reservation systems (airline, hotel, car rental), their agents where they have
one (hotels, from ch 7), and a payment provider. A corporate client adds a travel policy and
manager approvals. Narratively the operation still has a front office (intake, planning,
reservations), a mid office (policy checks, human approvals), and a back office (audit trail,
memory), but that framing is one paragraph of story, not a population target.

The business evolves in four phases that track the book's parts:

[cols="1,2,3", options="header"]
|===
| Phase | Book part | Business capability added

| Consumer booking core
| Part 1 (ch 1 to 6)
| Take a trip request, plan it as ranked candidate itineraries, let the customer choose, support
  the customer, inspire the undecided, remember everything that happened.

| Richer products + first B2B client
| Part 2 (ch 7 to 9)
| Hotel rates negotiated with the hotels' agents, trips reserved with the suppliers, a rental car
  added by choreography; a corporate client with a travel policy and manager approvals;
  disruption handling with rebooking and real compensation.

| Operational hardening
| Part 3 (ch 10 to 13)
| Payment that survives retries, replay after a bad prompt, cost governance, testing, security.

| Production
| Part 4 (ch 14 to 15)
| Observability, schema evolution, and migration to managed cloud services.
|===

=== Domain Map

The business divides into seven subdomains, each held one-to-one with a bounded context and an
event prefix, so prefix, context, and subdomain are one name. The one-to-one hold is a
deliberate simplification: where DDD would split a subdomain into several contexts (a language
that diverges inside it, or an external system's own model), this design answers with
aggregates inside one context and with edge adapters at the vendor's boundary. Each aggregate
has exactly one writer, the component that commits its state; entities have identity and a
lifecycle inside their aggregate; value objects are compared by value and replaced whole. The
map lists what the book models and nothing more. Booking is a supporting subdomain, and the
book's spine runs through it anyway, because every pattern attaches to the trip's lifecycle.

[cols="2,1,4,3", options="header"]

  one PII field segregated in ch 13) and the Conversation (one channel session, its Message
  entities, its Classification, and the trips it concerns). The Semantic Router classifies

Value objects every context shares: Money (amount and ISO 4217 currency), PlaceCode (IATA
airport or city code), DateRange, PartyComposition (adults, children, infants), PersonName.
The shared kernel is otherwise the event envelope, the identities, and the catalog of event
types. Every cross-context reference is by id; no context holds a copy of another's aggregate.

==== The Plan

The planning context's one aggregate, drawn because it is the shape every later chapter keys
off. A trip has one Plan; each planning request produces one Proposal in it; the customer
chooses one Candidate of the current Proposal or rejects them all.

The Requirements sit on the Proposal, not on the Plan, so a change of dates or budget mid-thread
keeps every earlier proposal readable against the requirements it answered. Proposal statuses:
proposed (the current one, awaiting the customer), superseded (a newer version exists),
accepted (the customer chose a candidate), rejected (the customer rejected them all). The
Candidate's items carry the supplier offers the Planner found; the negotiated rate a stay item
later wins is booking's fact, recorded on the Trip's Reservation, never written back into the
Plan.

==== Glossary

Each context's words, and their meaning there. The same word legitimately means
different things in different contexts; "request" and "confirmation" are the two cases shown in the
book.

[cols="1,1,4", options="header"]
|===
| Term | Context | Meaning

| trip request
| booking
| What the customer asked for: an origin, an ordered list of stops each with its dates or a
  window (one stop for a simple trip, several for a multi-city one), the travellers, a budget or
  an explicit "no limit", and the customer's preferences in their own words, including a car
  class when one is wanted. The fact that creates a trip.

| trip
| booking
| The aggregate, from request to confirmation or cancellation, holding the accepted candidate
  and its reservations. Servicing uses the same word for a journey already under way (ch 9), a
  second meaning across a boundary.

| booking
| booking
| The capability that takes a trip from request to confirmation, and the word's one meaning in
  the book. The booking context, the `booking` prefix, the booking workflow, and the Booking
  Agent are that meaning used as a label, the same shape as planning and its Planner. "A
  booking" is never a thing.

| reservation
| booking
| A commitment obtained from one supplier for one item of the trip, carrying the supplier's
  reference (an order id or record locator for a flight, a confirmation number for a hotel or
  a car). An entity inside the Trip, with the schema.org statuses pending, hold, confirmed, and
  cancelled. Booking is the agency's work; a reservation is what a supplier grants at the end
  of it.

| hold
| booking
| A reservation with a time limit: an unpaid order that expires, or a cancellable reservation.
  Created only at the reservation step; planning holds nothing.

| negotiated rate
| booking
| A rate a hotel's agent agreed with the Hotel Negotiator for one stay, with its terms and a
  validity: the hotel's commitment, not a quote. Recorded on the Reservation at the reservation
  step.

| request
| booking
| The customer's trip request (`TripRequested`) and, for a reply, what the customer said about
  a proposal (`CustomerReplied`). Both are written by whoever asks, in booking's published
  language.

| confirmation
| booking
| A supplier's confirmation of a reservation, and then the trip's own (`TripConfirmed`).

| plan
| planning
| The aggregate: everything planning has proposed for one trip, one per trip, one Proposal per
  request version.

| proposal
| planning
| One answer to one planning request: the requirements it answered, its ranked candidates, and
  its status. Immutable once published; a new request version produces a new one.

| candidate
| planning
| One concrete itinerary inside a proposal, ranked and labelled (cheapest, fastest, best
  value), with its items in travel order and the Planner's rationale. The customer chooses a
  candidate; the chosen one is the itinerary of record.

| itinerary
| planning
| The concrete flights and stays of one candidate, in travel order. The industry says offer or
  proposal before the sale and itinerary after; the book keeps "itinerary" for the candidate's
  content and for the event names that carry it.

| offer
| planning
| A supplier's priced, expiring, immutable option, and what the Planner selects from (NDC's
  Offer, OpenTravel's availability response). Its validity travels with the proposal to the
  customer.

| request
| planning
| A planning request (`ItineraryRequested`): the validated trip request, versioned, written by
  booking in planning's published language.

| confirmation
| planning
| The confirmation of an offer's price and availability before ordering (NDC's OfferPrice).
|===

Not used anywhere: "booking request", "booking record", "customer request", "travel
proposal", "itinerary proposal", "planning engine", "search request" (a search is the
Planner's private work).

The map's rules:

* **A component is placed by the facts under its ownership, not by its subject, and appears in
  exactly one row.** The Hotel Negotiator argues rates and reserves nothing, but a negotiated
  rate is a commitment the reservation step acts on, so it sits in Booking as an edge; the
  Booking Agent's reservation step owns `FlightReserved` and `HotelReserved`; the Rental Car
  Agent owns `CarRentalReserved` and does no planning, so it sits in Booking too. That
  asymmetry is the ch 7 choreography demonstration (a car added by reacting to
  `FlightReserved`, with nobody orchestrating it), not a modeling accident. A component that
  owns no facts (the Destination Research Agent) is placed by what it serves.
* **An event belongs to its aggregate's context.** The fact asserted by an event concerns one
  aggregate, and the event carries that aggregate's prefix.
  `booking.FlightReservationCancelled` is booking's although servicing decided it: the Recovery
  Agent drafts the compensation plan (`servicing.CompensationDrafted`) and the Booking Agent's
  compensation step mutates the reservation. The Duty-of-Care Monitor publishes
  `servicing.TravelRiskDetected` and never `booking.TripCancelled`; the Booking Agent reads the
  alert and decides.
* **A context is an open-host service for its requests.** A context publishes the schema of
  the requests it serves as its published language, and whoever asks writes the request in
  that language, under the serving context's prefix; the serving context answers with its own
  fact and writes every later fact about the thing requested. Booking serves
  `booking.TripRequested` and `booking.CustomerReplied`, written by the demo script (ch 3), the
  Front Desk and the Router (ch 4), and the partner adapter (ch 14); planning serves
  `planning.ItineraryRequested`, written by the Booking Agent (and by the demo script in ch 1
  and 2); support serves `support.SupportRequested` and destination serves
  `destination.InspirationRequested`, both written by the classifiers. A request is a fact that
  something is wanted, which cannot be rejected, only answered or left unanswered; a request
  that fails validation is answered with a fact (`booking.TripRequestRejected`). This is the
  one exception to the rule that a type is published from its own context, and it is why no
  context needs to know who its callers are: an entry point is one more writer of the
  published language, and nothing in the serving context changes. Every other type of a
  context is written by that context's components, and every transition of an aggregate by its
  one writer.
* **The edge observes, the owner commits.** A component at a context's edge publishes what it
  observed under that context's prefix, and the aggregate's writer records it with a fact of
  its own, causation set to the observation. The Hotel Negotiator's `booking.RateNegotiated`
  is recorded on the trip when the Booking Agent publishes `booking.ProposalReady`; the Rental
  Car Agent's `booking.CarRentalReserved` by `booking.CarReserved`; the payment provider
  adapter's `booking.PaymentAuthorized` by `booking.TripConfirmed`; the Router's
  `booking.SupplierUpdateReceived` (a supplier's email, ch 4) by whatever trip fact it
  warrants. The observation is an input to the owner, never a change to the aggregate, which
  keeps one writer per trip.
* **Planning has no side effects.** Reasoning publishes proposals, and one deterministic owner
  turns a proposal into a commitment. The Planner places no holds and negotiates nothing; a
  hold is a reservation, booking's entity, created at the reservation step, and a negotiated
  rate is booking's edge observation.
* **A high-risk side effect needs two independent keys.** The reservation step runs only on
  the Policy Gate's deterministic pass (`policy.PolicyCheckPassed`) and, when a violation was
  detected, the manager's decision on the ApprovalRequest. The agent's own reasoning is neither
  key (ch 13's dual key). Before ch 8 no Gate runs and the Booking Agent's configuration lets
  the step proceed on `ItineraryApproved` alone.
* **Delivery is a subscription.** Booking publishes facts and never addresses a channel. The
  Front Desk follows the trips its conversations own and decides how the customer hears each
  fact; the email delivery adapter does the same for trips the Router opened from email. The
  Booking Agent consumes only `booking.*` types and knows nothing about channels or
  conversations.
* **Synchronous queries across contexts are allowed for perishable answers nobody else acts
  on.** The Planner asks the Research Agent over A2A and reads the hotel sim's inventory over
  MCP because a search result expires in minutes and no other component reacts to it. A fact
  anyone else acts on goes on the broker (`05_data_consistency_and_state_model.adoc`).
* **`system` is the platform's technical namespace, outside the map.** BudgetExceeded,
  LivelockDetected, ModelFallbackActivated, EventQuarantined, and DutyOfCareSweepDue are
  technical events in ch 1's sense, facts about the system's own behavior, each owned by the
  mechanism that emits it. Platform components (below) stand in no row: they own only
  `system` facts and hold their state in platform-owned stores, and when one publishes a
  business-prefixed event it relays it for the owning component and sets the CloudEvents
  `source` to that owner.
* **Scheduled events carry the prefix of the asserted fact.** ApprovalTimedOut is `booking`,
  the workflow's expired wait, though the scheduler fires it, as is CustomerFollowUpDue; a wake
  with no business meaning (DutyOfCareSweepDue) is `system`.

=== The Platform

Components that serve every context and belong to none. They sit beside the map, not in it;
their own facts are `system` events, and none of them holds business state of its own: the two
guards keep their counters in the platform's `GuardStateStore`, never in a business context's
store.

[cols="2,1,3,2", options="header"]
|===
| Component | Chapter | What it does | `system` facts it emits

| Audit Consumer
| 1
| Appends every event to a durable audit record.
| none

| Observer/Reflector Agent
| 5 (both variants), writing the store from 6
| Projects the event log into Materialized Semantic Views through the `SemanticViewStore`;
  from ch 7 files lessons learned under the context path where they were learned.
| none

| Livelock guard
| 9
| Counts negotiation turns per `correlationid` in the `GuardStateStore`, the shape of the
  token budget guard, and stops a loop that exceeds the threshold; a guard over the thread,
  not state of any aggregate.
| `LivelockDetected`

| Token budget guard (economic circuit breaker)
| 11
| Meters token spend per `correlationid` in the `GuardStateStore` and throttles.
| `BudgetExceeded`

| Model fallback callback
| 11
| A LiteLLM callback that records a provider fallback as a fact.
| `ModelFallbackActivated`

| Guardrail Worker
| 13
| Consumes sensitive topics, verifies the producer's identity attribute, forwards verified

  producer), quarantines the rest.
| `EventQuarantined`

| Egress DLP Interceptor
| 13
| Scrubs PII from events bound for the external support vendor and the hotels' agents.

The `EventScheduler` and the outbox relay are Ports and infrastructure (below), not components:
they publish on behalf of whichever component scheduled or enqueued the event.

=== Identifiers

Identity conventions, in the book's order of introduction:

* **Event `id`** (CloudEvents core attribute): every event's own identity, minted as a
  UUID and **globally unique across the entire solution** by architectural decision. This is
  deliberately stricter than the CloudEvents minimum (unique per `source`): the reader's own
  system may not have a `source`, and a single unique key keeps references and table lookups
  one-column simple. The book explains this reasoning where CloudEvents is introduced
  (`ch02_semantic_data_contracts`).
* **Causation:** a reply carries the globally unique id of its request. Ch 1's
  `ItineraryProposed` holds the `ItineraryRequested` id as a `request_id` payload field, and the
  demo script matches on it. `ch02_correlation_id` promotes it to a `causationid` extension
  attribute (one attribute, since ids are globally unique); ch 14's `traceparent` carries
  parent identity for observability, not business causation.
* **`correlationid`:** the execution-thread key (`ch02_correlation_id`), the conversation's id,
  minted at the first customer message (or by the demo script that stands in for it) and
  copied to every event of the execution; it replaces the synchronous call stack. Causation is
  a link, correlation a label: following causation walks the thread hop by hop, filtering on
  correlation returns it whole. A second thread on the same trip (ch 8's duty of care, ch 9's
  disruption) gets its own correlation id.
* **`partitionkey`:** the standard CloudEvents partitioning extension, on every event from the
  ch 2 practical, carrying the id of the event's aggregate: the trip's id on every booking,
  planning, and policy fact, the conversation's id on every customer fact, and, where the
  context holds no aggregate, the id of the trip concerned or, before a trip exists, the
  conversation's. Ordering by key is part of the broker contract: events sharing a
  `partitionkey` are delivered in publish order, one at a time, to one consumer. The adapter
  maps the attribute to whatever its broker orders by (Kafka's record key, Pub/Sub's ordering
  key, a message group id), and a broker that cannot order by key is unsupported or reached
  through a workaround. The contract's three conditions (one topic per context, one key at a
  time, a version check in the store) and the supported brokers are in
  `05_data_consistency_and_state_model.adoc`; the mapping is in `04_implementation_design.adoc`.
* **The trip's id** is the id of the `booking.TripRequested` event that created it (in ch 1
  and 2, the id the demo script mints for its `planning.ItineraryRequested`). On that event
  `id` and `partitionkey` coincide by construction and diverge afterwards: the next event has
  its own id, and every trip fact carries the trip's id as its key. Requesters mint only the
  event id, minted by every producer for every event; the owner's checks already exist in the
  architecture: the id is a UUID (the ch 2 contract, enforced at the container boundary), and
  the id is not already in the store (idempotent consumption, so a redelivery is skipped and
  never answered with an error event).
* **The Plan has no id of its own.** It is keyed by the trip's id, one per trip; each
  `planning.ItineraryProposed` is an immutable proposal identified by its own event id and
  carrying its version, and `booking.ItineraryApproved` names the approved proposal by that
  event id and the chosen candidate by its rank.
* **`promptversion` and `modelversion`** (from ch 10): stamped by the container on every event
  an agent publishes, from the agent's own configuration. No consumer reads them to act; the
  dead-letter tooling, the replay script, and the audit record read them to answer "which
  logic produced this".
* **The customer reference:** a `TripConfirmed` payload field from ch 8, assigned by the
  Booking Agent against the `WorkflowStateStore`: six characters from a 32-character alphabet
  (letters without I and O, digits 2 to 9), random with a clash check, never a sequence and
  never recycled. A reference identifies and never authorizes (ch 13). Until ch 8 the demos
  show no reference.
* **`contextpath`** (from ch 7.6): hierarchical context scoping on the trip's id, e.g.
  `/trips/{trip_id}/paris/hotel`.
* **`identitytoken`** (from ch 13): a signed identity extension attribute per agent whose
  subject must match the CloudEvents `source`, verified at the container boundary on
  consumption and by the Guardrail Worker on sensitive topics, so the rule is portable across
  brokers. Kafka principals with topic ACLs in the compose stack are defense in depth and the
  enforcement view of the single writer.

=== Realism rule: what is an agent and what is not

Agents exist only where non-deterministic reasoning is genuinely needed: where inputs are
unstructured or the decision is open-ended. That is intake and classification (the Front Desk's
classifier, the Router), the Planner's composition of ranked candidates and its sub-agents'
judgement over routes and hotels, the Negotiator's argument with a hotel's agent, the crew's
inspiration, the Recovery Agent's compensation plan, the Monitor's impact judgement, and the
Rental Car Agent joining a flow with no orchestrator behind it. Everything else is deterministic
code or a simulated vendor: the Booking Agent's validation and its reservation step, the Policy
Gate, the payment provider adapter, the Planner's validator node, the projections, and every
simulator. Reasoning proposes; a deterministic owner commits.

Chapter 1's request-response scenario and its cascade figure use design-true components only:
the Booking Agent calls the Itinerary Planner Agent, the Planner calls the airlines' and
hotels' independent reservation systems and then its model, and the Planner's inference is the
slow or dead callee. Deterministic vendors are present from the first chapter, the reader's
mental picture of the cast never changes as the book progresses, and the durability example
of 1.3 (the Planner comes back after 20 minutes and the event is still there) is the failure
1.6's demo then runs; the connection-explosion figures stay deliberately generic.

=== Realism kept as texture

The industry's standards shape the model without becoming components for the reader to hold in their
head:

* **Language and relationships** come from the standards and live in the glossary and the map:
  NDC and ONE Order (an Offer is a supplier's priced, expiring, immutable proposal; an Order is
  the durable purchase record with its items), OpenTravel (a hotel reservation is a room stay
  under a rate plan with a confirmation number; a car reservation is a vehicle class at a
  pickup and return), schema.org (a Trip has an itinerary; a Reservation has a status of
  pending, hold, confirmed, or cancelled), ISO 31030 (assess travel risk before a trip, monitor
  during it, respond to incidents), PCI DSS (the agency never holds card data; a provider
  does).
* **Simulator surfaces** are shaped like the real supplier APIs in a printable subset,
  Amadeus-like rather than full IATA schemas (the simulator table below); endpoints and field
  names, never schemas.
* **Payloads** borrow names and codes inside the book's own Pydantic models: IATA airport and
  airline codes, ISO 4217 currencies, ISO dates, ACRISS vehicle classes, offer validity,
  record locators, and fare conditions (change and refund penalties), the agents' reasoning
  material.
* **Standards are named in prose only where they explain a design choice:** NDC and ONE Order
  beside event sourcing's single record of the trip (ch 6); schema.org's statuses in the
  glossary; ISO 31030 in a sidebar beside the Duty-of-Care Monitor (ch 8); ACRISS beside the
  Rental Car Agent (ch 7); PCI DSS in one sentence beside the payment provider adapter
  (ch 10).
* **Excluded:** NDC's message families, OpenTravel's XML, and the airline industry data model
  as a whole.

=== Ports and infrastructure

Ports (all outline-established, unchanged): `EventBroker`, `EventScheduler`,
`WorkflowStateStore`, `SemanticViewStore`, `BlobStore`, `InboxStore`, `BarrierStore`,
`IdempotencyStore`, and the platform's `GuardStateStore`. The low-level design (exact port
signatures, the event envelope, minting rules, naming, and repo layout conventions) is
`04_implementation_design.adoc`.

**`EventBroker` subscription capabilities.** Beyond per-event-type subscription, the port
offers subscribe-all (or an event-type prefix), the intersection floor across backends,
never arbitrary regex. The Kafka adapter implements it with a regex topic subscription over
the application's namespace, picking up newly created topics on the periodic metadata
refresh; an adapter whose backend has no native patterns emulates the promise from its own
event-type-to-topic registry; on GCP (ch 15) the mechanism moves into infrastructure, where an
Eventarc Advanced enrollment feeds a pipeline that pushes to the consumer's ingestion
endpoint, so the consumer does not subscribe at all. From ch 1 the adapter maps one topic per
context and filters each subscription by type, and agents see neither. Consumers
therefore come in both invocation models the container supports (`ch02_agent_container`): a
pull loop, or a push endpoint the infrastructure delivers into. The audit consumer is the
standing beneficiary: it sees every event, including types added chapters later, with no code
change.

**Model access: LiteLLM, not a Port.** There is deliberately no hand-written model port.
The book's Ports exist to abstract infrastructure owned by the architecture; model access is
already commoditized by **LiteLLM**, a mature library exposing 100+ providers (cloud APIs and
Ollama alike) behind one interface, with fallbacks, retries, rate limits, and cost tracking
built in. Writing a port over it would model exactly the anti-pattern warned against in the book,
abstracting an abstraction. Concretely:

* **Plain-Python agents** call the LiteLLM SDK directly; the model is a config string
  (`gemini/...`, `anthropic/...`, `ollama_chat/...`), and the cloud-key-default /
  Ollama-fallback strategy is a LiteLLM `fallbacks` configuration rather than code.
* **ADK agents** use ADK's own `LiteLlm` wrapper (`Agent(model=LiteLlm(model=...))`); the
  framework's native model abstraction *is* LiteLLM, which is the precedent for this decision.
* **LlamaIndex, LangGraph, and CrewAI agents** either use their LiteLLM integrations or
  point their OpenAI-compatible client at a LiteLLM endpoint (CrewAI's own LLM class is built
  on LiteLLM), so either way the model choice stays in config.
* **Chapter 11** divides cleanly: mechanical provider fallback on outage and predictive
  throttling against provider limits are LiteLLM configuration (the fallback chain and the
  per-deployment token and request rate limits); the *economic circuit breaker* (token budget
  per `correlationid`, spanning agents and frameworks) remains the book's own pattern on the
  `GuardStateStore`, because no gateway can know workflow identity across a polyglot swarm;
  the supplier circuit breaker (below) is the book's own code as well, since it guards a
  dependency outside LiteLLM's reach.
* **Chapter 15**'s swap to Vertex AI / Bedrock becomes a one-line model-string change, a
  cleaner zero-lock-in proof than a custom adapter.

**Supplier clients carry a circuit breaker.** Every call from an agent's tool to a supplier sim
goes through a shared client in `lib/travel_agency` with a per-dependency circuit breaker:
repeated timeouts open it, calls fail fast while it is open, and a trial call closes it again.
An open breaker is not an exception raised to the container but an observation returned by the
tool to the reasoning loop ("supplier unavailable"), so the agent proposes alternatives instead
of waiting on a timeout. Ch 11 demonstrates it on the Airline Reservation System sim's
slow-vendor mode; the model's counterpart is LiteLLM's fallback chain, so an agent's two failing
dependencies have two breakers.

Infrastructure: Kafka (KRaft, single container) + Kafka Connect HTTP sink for push, PostgreSQL,
MinIO, Redis (alternative broker adapter), Ollama, LiteLLM (SDK in-process), APScheduler relay
process, OTel + Jaeger, Docker Compose (each chapter's compose file *is* that chapter's
stack; profiles only for optional pieces like the UI shell), Terraform (ch 15).
