= Travel Agency Application, System Design: Data Consistency and State Model
:toc:

// Design documentation for the Travel Agency application built across the book. Companion
// documents: 01_system_overview.adoc (components, domain map, identifiers),
// 02_workflows_and_events.adoc (workflows + events), 03_chapter_mapping.adoc (chapter mapping),
// 04_implementation_design.adoc (implementation surfaces and conventions). This document defines
// the architectural strategy for handling state, consistency, and ordering in a distributed,
// eventually-consistent system.

== Overview

This document describes how the Travel Agency system ensures consistency across its components
without requiring synchronous coordination. The strategy rests on four pillars: **one writer
per aggregate**, with the aggregate's state in that writer's store and every change
announced as an immutable fact, **CQRS** (Command Query Responsibility
Segregation) to separate writes from reads, **ordering per key** as part of the broker contract
(an aggregate's events arrive in publish order), and **eventual consistency** across aggregates
enforced through causation tracking, staging, and idempotent read model updates.

== The Write Model: State in the Store, Facts on the Broker

An aggregate's current state is kept by its one writer: the Trip is one document in the
Booking Agent's `StateStore`, loaded before an activation and committed after it with the
id of the event that caused the change (The Trip's Operations, below). Every state
transition is also announced as an immutable event, the fact that it happened, published
after the commit. The store is the authority on what an aggregate is now; the events are
the authority on what happened, and the source of every read model. The aggregate itself is
not event-sourced: the Trip is never rebuilt from its events, and ch 6 teaches event
sourcing on the log as the record behind the read models.

* **Aggregates:** the spine has two aggregate roots, the Trip (booking) and the Proposal
  (planning). Each event belongs to exactly one aggregate. A Trip's events name the trip id,
  assigned by the Booking Agent's store when the Trip is created and announced by
  `booking.TripCreated`; a Proposal's id is a `proposal_id` generated by the Planner, and every
  proposal is keyed by the trip id, so `planning.ItineraryRequested` (booking's request,
  written in planning's language) and `planning.ItineraryProposed` name the trip id too, both
  on planning's topic and therefore ordered against each other. A trip accumulates proposals. A payment is not an aggregate:
  the Payment is an entity inside
  the Trip, and `booking.PaymentRequested` and `booking.PaymentAuthorized` are trip events. The
  other contexts' aggregates (Customer and Conversation, ApprovalRequest, Document) follow the
  same rules with their own writers and topics; this document works through the spine.
* **Immutability:** events are written once and never modified. Correction is a new event
  (e.g., `booking.TripCancelled`), not an edit to an existing one.
* **Replay and Rebuilding:** a read model is rebuilt from the events. If one is corrupted or
  stale, replaying the event log rebuilds it without loss of information. Until ch 8's
  outbox, a fact lost between a commit and its publish is missing from the log (The
  Activation Protocol, below).

== CQRS: Separation of Writes and Reads

CQRS means the *model used to answer queries* is separate from the write model and derived
from its events.

* **Write Model (the aggregate and its facts):** the aggregate in its writer's store, changed
  only through its operations. Agents publish facts, never commands. These events carry the fact (e.g.,
  "customer requested a trip for 2 travelers"). Once published, an event is immutable. It does
  not express an opinion about whether the request is valid; the event is the record of the fact
  that it was requested.
* **Read Model (Projected State):** a separate service or component listens to events and builds a
  materialized view, a queryable snapshot. For example, the Observer's `TripView` (ch 6) says
  "Trip 123 has status = 'requested', traveler count = 2". This view is mutable and can be
  rebuilt from scratch. The `StateStore` is not a read model: nothing queries it but the
  activator, by the trip's id.
* **Eventual Consistency:** the read model lags behind the event log. When an event is published,
  the read model has not yet been updated. A subscriber listening for events and projecting them
  into the read model does so at its own pace. If the subscriber is fast, the lag is milliseconds;
  if congested, it may be seconds. But the read model eventually matches the history.

== Single Writer Principle: One Writer per Aggregate

Only one component (or one component's replica set, serialized by key) publishes the events
that change a given aggregate. The Booking Agent is the single writer for Trip events; the
Itinerary Planner is the single writer for Proposal events. Two exceptions are part of the
principle, not violations of it:

* **A context's requests.** A context is an open-host service for the requests it serves: it
  publishes their schema as its published language, and whoever asks writes the request under
  the serving context's prefix. `booking.TripRequested` creates the Trip rather than changing
  it, and `booking.CustomerReplied` records what the customer said about a proposal, in the
  customer's words, a fact about the request rather than a change to the trip, read by the
  Booking Agent, which alone commits what it means; the demo script (ch 3), the Front Desk
  (ch 4), the Router (ch 5), and a partner adapter (ch 14) write them. `planning.ItineraryRequested`
  is written by the Booking Agent (the demo script in ch 1 and 2), `support.SupportRequested`
  and `destination.InspirationRequested` by the classifiers. Every transition of the thing
  requested has one writer.
* **Edge observations.** The Hotel Negotiator's `booking.RateNegotiated`, the Rental Car
  Agent's `booking.CarRentalReserved`, the payment provider adapter's
  `booking.PaymentAuthorized`, and the Router's `booking.SupplierUpdateReceived` are
  observations published by components at booking's edge. They are inputs to the Booking
  Agent, which records each with a fact of its own (`booking.ProposalReady` after the barrier,
  `booking.CarReserved`, `booking.TripConfirmed`), causation set to the observation. The
  aggregate still has one writer.

This principle does not prevent reads. The Audit Consumer reads all events. The Booking Agent
consumes `planning.ItineraryProposed` to know what has been proposed (a read). But when the
Itinerary Planner answers a request, only it publishes the `planning.ItineraryProposed`. The
customer's decision on a proposal is booking's fact (`booking.ItineraryApproved`,
`booking.ItineraryRejected`, `booking.TripChanged`, or `booking.ClarificationRequested` when
the reply does not settle it), published by the Booking Agent; the
Planner consumes only the approval, to mark the chosen itinerary, and learns of a rejection or
a change through the next `planning.ItineraryRequested` the Booking Agent writes. The two writers share a key value, the trip id, and share neither a topic nor a
writer.

=== Multiple Replicas of the Same Writer

The single writer principle does not require a single process. A component may have multiple
replicas for scaling or availability, and the ordering contract serializes them: the broker
assigns each key's lane (the Kafka partition holding it, a Pub/Sub ordering key) to one replica of the group
at a time, so at any moment exactly one replica handles a given trip, and it handles that trip's
events one at a time, in order. No lock and no coordination protocol is needed.

The one gap is a rebalance. A replica in the middle of an activation when the broker reassigns
its lane can write after the new owner has moved on. The store's version check is the fence: a
write carrying a stale expected version of the aggregate is rejected, and the rejection returns
to the handler as an error (`04_implementation_design.adoc`). The demos never hit it; ch 8 states
it in one sentence.

== Causation Chains: Linking Events Across Aggregates

When one aggregate's event triggers a change in another aggregate, the two events are linked by
the **causation id** (`causationid`) and the **correlation id** (`correlationid`) extension
attributes.

* **Causation id:** when the Planner receives a `planning.ItineraryRequested` event, it
  publishes `planning.ItineraryProposed` with `causationid` set to that event's id, and the
  request's own causation points at the `booking.TripCreated`, `booking.ItineraryRejected`, or
  `booking.TripChanged` that led the Booking Agent to write it. The read model can trace
  backward: "this proposal answered this request, which followed this rejection."
* **Correlation id:** all events in a logical flow share a correlation id, an id of its
  own, generated by whoever starts the workflow (the customer channel, or the demo script
  standing in for it) and inherited by everything that follows, the trip request included;
  the conversation's id is separate, and is data. The audit log can then
  trace the entire workflow by correlation id. A second workflow on the same trip (ch 8's duty
  of care, ch 9's disruption) generates its own.

Causation chains are stored in event `attributes` (see `04_implementation_design.adoc`). They
enable tracing without requiring real-time synchronous calls between components.

== Aggregate Boundaries: Why Trip and Proposal Are Separate

A naive design might fold the proposals into the Trip, reasoning that they are keyed by the
trip anyway. This design is rejected because:

* **Different Writers:** the Trip is created and changed by the Booking Agent; a Proposal is
  written by the Planner. One aggregate would have two writers, or one writer relaying the
  other's decisions.
* **Concurrency:** a customer can change the request (`booking.TripChanged`) while the Planner
  is composing a proposal for the original one. In one aggregate the two updates conflict and
  must be serialized by a lock or a consensus step. As separate aggregates both proceed: the
  Booking Agent commits the change and writes a new request, the Planner's running activation
  takes it from its inbox, answers the older request with `planning.ItineraryRequestSuperseded`,
  and restarts from its checkpoint, and the pairing of change, request, and proposal is
  explicit through causation and the proposal's id.
* **Different Lifecycles:** a Proposal is immutable once published, and a trip accumulates them
  until the customer chooses an itinerary from one; the Trip lives on through reservation,
  confirmation, servicing, and cancellation.

The same reasoning decides the other boundaries. The Payment is *not* a separate aggregate: one
writer (the Booking Agent) records it, the provider adapter only observes, and the idempotency
against the real side effect lives at the adapter's `IdempotencyStore`, so a second aggregate
would add a lifecycle without adding a writer. The ApprovalRequest *is* separate, because a
different party (the manager, through the approval console) decides it and its record outlives
the trip's wait.

By keeping Trip and Proposal separate, each maintains a single writer, a clear lifecycle, and
independent concurrency. Trade-offs:

* **Cross-Aggregate Reads:** the Booking Agent learns the current proposal from
  `planning.ItineraryProposed`, not from a synchronous call; its view may lag.
* **No Atomic Transactions:** a trip change and the proposal it causes cannot be made atomic.
  The change is published first; the proposal follows. If the proposal never arrives (a crash),
  the change is already committed and the trip waits, which is the durable state machine's
  normal condition (ch 8). Compensation is a saga (ch 9), never a rollback.

== Read Models: Materialized Views and Idempotent Projections

A read model is built by a **projection**, a component that listens to events and updates a
query-able store (a database table, an in-memory cache, a materialized view).

=== Idempotent Projections

Brokers guarantee at-least-once delivery, which means an event may be redelivered (e.g., if the
consumer crashed or was slow to acknowledge). A projection must be idempotent: applying the same
event twice produces the same final state as applying it once.

Example: a read model stores `trip_status`. When `booking.TripCreated` arrives with trip id 123,
the projection updates the row for trip 123. If the same event is
redelivered due to a consumer restart, the projection receives it again. An idempotent projection
checks: "have I already processed this event?" If yes, skip it. If no, process and record it.

Idempotency is implemented via **event deduplication by event id**. Each event has a globally
unique id. The projection tracks which event ids it has processed. Before updating state, it
checks: "have I already processed event id X-Y-Z?" If yes, skip it. If no, process and record
the id. This is required for all consumers; the ordering contract makes a redelivery arrive in
order, not disappear.

=== Handling Out-of-Order Events: Across Topics Only

Within a key on one topic, order is guaranteed by the contract: all events for Trip 123 on the
booking topic are delivered in publish order, and the consumer's idempotency guard handles
redeliveries.

Out-of-order arrival occurs only *across topics*. The Booking Agent writes
`booking.TripRequested`'s consequences on the booking topic and `planning.ItineraryRequested`
on the planning topic, and the Planner's `planning.ItineraryProposed` follows on the planning
topic. Two lanes carry the same key value, so nothing orders them against each other: a view
joining both topics (the Observer's `TripView`) can see the proposal before the
`booking.TripCreated` that started it. The Booking Agent itself is not exposed, since it wrote the request only after
recording the trip, and a crash between the two is ch 8's durability lesson.

A robust read model handles this by **staging**, the `InboxStore` shape of ch 7, with the
causation chain naming the prerequisite:

* If `planning.ItineraryProposed` arrives first, the projection stages it under the trip id
  until the `booking.TripCreated` in its causation chain (proposal, planning request, trip
  created, trip request) has been applied, then applies it.
* If `booking.TripCreated` arrives first, the projection records the trip, and the proposal
  applies on arrival.

In both cases the final state is the same, because the prerequisite is explicit. A projection
that joins topics tolerates this arrival order; within a key on one topic, order is guaranteed.

== Consistency Guarantees: Within and Across Aggregates

The system guarantees:

* **Strong Consistency Within Aggregates:** events for a single aggregate (e.g., Trip 123) are
  delivered in order and processed serially, one at a time, by one consumer. The read model sees
  them in publish order. Combined with idempotency, this ensures an aggregate's view is always
  consistent with its event history. This holds on every supported broker (Ordering
  Guarantees, below); there is no adapter on which it does not.
* **Causal Consistency Across Aggregates:** if event A (in one aggregate) causes event B (in
  another), the causation chain (B's `causationid`) explicitly links them. Read models use it to
  stage and resolve dependencies regardless of arrival order.
* **At-Least-Once Delivery:** every event is delivered at least once. Exactly-once is not
  guaranteed (the broker delivers at-least-once, and retries on failure). Idempotent projections
  tolerate duplicates.
* **Durability:** once an event is written to the broker, it persists until the retention period
  expires (e.g., Kafka's log retention).

The system does NOT guarantee:

* **Immediate Consistency:** a query to a read model immediately after publishing an event may not
  reflect that event. The projection is still applying it. This lag is typically milliseconds but
  may be seconds if the projection is congested.
* **Total Ordering Across Keys or Topics:** events with different keys have no defined order
  (event A for Trip 1 and event B for Trip 2 may arrive in any order), and events with the same
  key on different topics have none either. Cross-topic read models stage by causation.
* **Atomic Multi-Aggregate Transactions:** updates to two separate aggregates cannot be made
  atomic. One succeeds and is durable; the other may fail. Compensating logic is required.

Clients must accept these trade-offs:

* After publishing a fact (e.g., a trip change), the client waits for the projected read model
  to reflect the change before considering the operation complete. This waiting is the
  "eventual" part.
* If a client needs to coordinate updates across two aggregates, it publishes the first, waits for
  the read model, publishes the second (if needed), and waits again. If the second fails, the
  first is already committed; a compensating event may be needed to revert it.

== The Activation Protocol: What It Does Not Yet Close

The activator's protocol for a stateful agent (`04_implementation_design.adoc`, The Agent
Activator) is: validate, create or load, invoke, check the answer, commit the state and the
handled event id in one transaction, publish, acknowledge. Reviewed against the chapter 3 code
on 2026-11-02, it guarantees four things on every supported broker: no state is committed
unless the activation produced a valid answer; no committed state is lost; no event changes
one aggregate twice; and one replica at a time writes a given aggregate, with the version
fence as the backstop. What it does not guarantee is listed here, each gap with the mechanism
and the chapter that closes it, so each chapter's demo is read against the guarantee in
force at that point and not against the finished system. The closings were decided on
2026-11-03.

* **A fact lost between the commit and the publish** (closed by the Agentic Outbox, ch 8).
  The commit and each publish are separate calls, and the shield around them holds against
  cancellation only. A kill after the grace period, an out-of-memory kill, or a broker
  refusing the publish leaves the state advanced and the fact unpublished, and the redelivered
  inbound event is acknowledged as handled. Nothing records the lost fact, so a trip at
  `planning` with no `planning.ItineraryRequested` on the broker stalls silently. The outbox
  writes the facts, with their ids, in the commit's transaction, and a relay publishes them in
  commit order per key. What remains after it is the relay's own at-least-once, under the same
  id, which is deduplication by id (next item).
* **A stateless agent's facts duplicated under new ids** (closed by derived ids, built from
  ch 3 and taught in ch 10). An agent without a `state` declaration (the Itinerary Planner) has
  no handled check, so any redelivery runs it again and its answer leaves under a fresh id:
  after a crash before the offset commit, after a rebalance, and on every seek-back after
  another key's failure, which re-fetches the finished records behind the failed one on the
  same partition. The Booking Agent is covered by `request_id`; a projection, or any other
  consumer, sees two events. The closing is the inbound event as the upstream idempotency
  key: the activator derives the id of each fact answered at the end of an activation from
  the component's name, the inbound event's id, the fact's type, and its ordinal among that
  type, as a name-based UUID (v5), so a rerun states the fact under the same id and every
  consumer deduplicating by id drops the second, the stateful ones through `handled`. The
  component's name keeps two components answering one event apart, and the type keeps a
  rerun answering in another order on the same ids. A name-based UUID is a hash of fixed
  length, so a chain of any depth carries no history in its ids, and its collision odds are a
  random UUID's. The first stated fact wins, which is the right rule for an LLM whose second
  answer may differ. It is always on, since nothing before ch 10 observes how an id is
  derived; a publisher outside an activation (a demo script, a channel) has no inbound event
  and keeps a random id. A fact stated mid-activation through `eda.publish` leaves through
  the same path and gets a derived id too, so a rerun stating the same facts in the same
  order repeats their ids; the side effect behind such a fact is repeated all the same, and
  that belongs to ch 8's durable checkpoint (`04_implementation_design.adoc`,
  Publish tools).
* **A rebalance runs one activation twice** (accepted; the fence, ch 8). On revocation the
  adapter commits the watermark and forgets the partition while the lane in flight runs on,
  and the new owner fetches the same record. Both invoke the agent, and the LLM, on the same
  version. The fence lets one commit and refuses the other with `StaleVersion`; the loser's
  redelivery is found handled and skipped. The state is consistent, and the cost is a second
  LLM call per in-flight activation per moved partition, with an arbitrary winner. The
  alternative, canceling a revoked partition's lanes before their commit starts, cuts the
  second call but, under Kafka's eager rebalance protocol, cancels every running activation
  on every membership change. The design keeps the fence alone and names the alternative in
  ch 8.
* **One failing event throttles the replica and burns tokens** (closed by `max_attempts`,
  built from ch 3 and set in ch 10). After a failed lane the loop fetches nothing until the lanes in flight
  drain, pauses `retry_delay`, seeks back, and fetches again, with no cap. Between retries
  every other partition advances by one batch, so the replica is throttled rather than
  stopped; the failed record's own partition does not advance past it, and the finished
  records behind it on that partition are fetched and handled again on every cycle: a stateful
  agent skips them by `handled`, and a stateless agent runs them again, one LLM call per
  record per cycle, without end. The closing is an attempt count per record in the adapter and
  `max_attempts` on its constructor, unbounded by default so that chapters 3 to 9 retry as
  they do today: once the cap is reached, the record goes to `dlq.<context>` with its key,
  is marked finished, and the watermark moves past it. Only the activation's own failures
  count (`NoAnswer`, `RejectedAnswer`, an exception from the agent's code): a port's failure,
  the store or the broker unreachable or a `StaleVersion`, retries without a cap, because
  the event is sound and dead-lettering it for an outage would be wrong. The activator tells
  the two apart by raising its port calls' failures as `PortFailure`, which `StaleVersion`
  extends, and the adapter counts every other failure.
* **Two silent acknowledgments** (closed in ch 10, poison pills). A malformed event, and an
  event about a state missing from the store, are raised by the activator as a `PoisonPill`, and a record that is no CloudEvent by the
  adapter itself; the adapter acknowledges a `PoisonPill` until a cap is set;
  a store restored from an older backup meets the second for every trip opened since. From
  ch 10 both go to `dlq.<context>` instead, with the record's key, so that a store restored
  from a backup leaves a replayable trace rather than dropping every newer trip's events.
  Before the cap and the DLQ topic are configured, both stay acknowledged warnings.

Two narrower gaps stay with the Kafka adapter and are recorded under Subscription Mechanics
in `04_implementation_design.adoc`: a consumer group killed before its first offset commit
resets by `start` and skips its in-flight event, and the shield lets a second cancellation
through at once, so a forced shutdown during a commit-and-publish is the first gap above.

== Ordering Guarantees: The Contract

Within-aggregate order **is part of the `EventBroker` contract** (`ch04_consumer_concurrency`),
though the frozen `publish` surface takes no key: the key is the
CloudEvents `partitionkey` extension attribute, on every event of a class declaring `order_per`, and the
adapter maps it to whatever its broker orders by. The contract sentence: *events sharing a
`partitionkey` are delivered in publish order, one at a time, to one consumer.* It promises
order per key, never partitions; partitions are one of the adapter's ways of keeping it.

The key is a group label, never a per-event ordinal: events sharing a key form one lane, and a
key unique per event is no order at all. There are no sequence numbers, no highest-wins
resolution, and no staging inside an aggregate; order is the transport's, per key, never the
consumer's by content.

Three conditions make the promise hold, each stated where it lives:

1. **All of an aggregate's events share a topic.** Ordering brokers order per key within one
   topic, so two events of one aggregate on two topics are unordered whatever their key. The
   adapter therefore maps one topic per context from ch 1, with the type inside the event and
   subscription by type filtered in the adapter (`04_implementation_design.adoc`).
2. **The adapter handles one key at a time and commits by watermark**: per-key lanes, with
   keys concurrent and the commit trailing the slowest (the consumer rule in
   `04_implementation_design.adoc`).
3. **A version check in the store fences a stale replica** (Multiple Replicas, above).

Two mechanisms build the lanes, and who builds them differs:

**Partitions (Kafka, Redpanda, Azure Event Hubs, RabbitMQ Streams):** the adapter uses
`partitionkey` as the record key, so all events for a given aggregate hash into one of a fixed
number of physical logs. The broker delivers a partition in order and assigns the whole partition
to one replica of a group, ordering unrelated keys along with related ones; the adapter then
builds the per-key lanes inside the partition itself, so strangers sharing a partition do not
wait for each other (`04_implementation_design.adoc`, the consumer rule).

**Ordering keys (Google Pub/Sub with ordering enabled, Azure Service Bus sessions, SQS FIFO
message groups):** the adapter uses `partitionkey` as the ordering key, the session id, or the
message group id, a logical lane per key value. The broker holds the next message for a key until
the previous one is acknowledged.

Both solve the reserve-and-cancel race the same way: `booking.FlightReserved` and
`booking.FlightReservationCancelled` travel on the booking topic with the trip's id as key,
arrive in order, and reach one replica. Both need the one-topic condition, since lanes are
scoped to a topic. On either, a slow activation holds up only its own key.

=== Supported Brokers

The backends available to the book's adapters. Agents never learn which adapter is
underneath, and the guarantee is the same on every supported one.

* **Supported, ordering per key:** Kafka and Redpanda (record key); Azure Event Hubs (partition
  key; Kafka-compatible); RabbitMQ Streams (partitioning by key); Google Pub/Sub (ordering keys,
  enabled on the subscription); Azure Service Bus (sessions); AWS EventBridge only behind a FIFO
  SQS queue (message group id), at the cost of a hop; Redis Streams by sharding streams per key
  hash, one consumer group per shard.
* **Unsupported, no per-key order:** AWS EventBridge standalone, Azure Event Grid, RabbitMQ
  classic queues (per-queue order exists but not per key, and one queue per aggregate does not
  scale).
* **To verify at ch 15 planning:** Google Eventarc's ordering guarantee behind Eventarc Advanced,
  and the exact Redis Streams sharding; the ch 15 adapters are written only against brokers
  confirmed in the first list, and the book's list of replacement brokers (ch 1.5) is
  restricted to them.

**An adapter that cannot order per key is not an adapter of this book.** The port promises order
per key, so a backend without it is unsupported or reached through a workaround from the first
list; it never ignores the key silently.

=== Across Topics

Lanes stop at the topic boundary. The Booking Agent publishes trip events to the `booking` topic
keyed by the trip id, and the planning request to the `planning` topic keyed by the same id;
the Planner publishes proposals to the `planning` topic keyed by the same trip id, by design,
since every proposal is keyed by the trip. Request and proposal share a topic and a key, so a
proposal never overtakes the request it answers. Same key value on different topics: nothing
orders one against the other, and a read model needing both (e.g., "Trip 123 with its
current proposal") must join them.

Co-partitioning across topics is not the answer: lanes are per topic, a Kafka join would tie two
topics to identical partition counts and one consumer, and an ordering-key broker has no such
notion at all. In the Travel Agency system **the solution is causation and staging**:

1. The Planner reacts to `planning.ItineraryRequested`; the request carries the validated
   requirements and, on a re-plan, the reason, so the Planner reads no trip model before
   proposing; what it already proposed it reads from its own store.
2. The Planner publishes `planning.ItineraryProposed` with `causationid` pointing to the
   request, keyed by the trip id; the request's causation points at the booking fact that led
   to it.
3. The Trip records proposals as they arrive; the trip exists, because the
   Booking Agent wrote the request after recording it.
4. Cross-topic views (the Observer's `TripView`, ch 6) are built from every topic, stage what
   arrives early, and reconcile by causation, scoped by `contextpath` from ch 7.

This tolerates the out-of-order arrival of events from different topics without a global order.

== Broker Selection and Implementation Trade-offs

**No broker-specific code.** The design does not branch on broker type. A producer sets
`partitionkey` once and never learns which adapter is underneath. What used to vary with the
adapter, whether an aggregate's events arrive in order, no longer varies: every supported adapter
keeps the contract, and a projection may assume within-aggregate order everywhere. The ch 15
cloud chapter names its managed adapters, all from the supported list, so a reader
moving the system keeps the guarantee by construction.

== Application to the Travel Agency

=== Aggregates

* **Trip:** owned by the Booking Agent. Created on `booking.TripRequested` (written by whoever
  asks, keyed by the conversation's id) under an id assigned by the store, announced by
  `booking.TripCreated`, the first event keyed by the trip id; changed by `booking.TripRequestRejected`,
  `booking.ProposalReady` (recording a proposal, and from ch 7 the negotiated rates),
  `booking.TripChanged` (the customer changes the request), `booking.ItineraryApproved` and
  `booking.ItineraryRejected` (the customer's decision on a proposal, the approval naming the
  proposal's id and the chosen itinerary's rank), `booking.FlightReserved`,
  `booking.HotelReserved`, `booking.ReservationFailed`, and `booking.CarReserved` (recording the
  Rental Car Agent's observation), `booking.ApprovalRequested` and `booking.ApprovalTimedOut`
  (ch 8), `booking.RebookingProposed` (ch 9), `booking.PaymentRequested` with the recording of
  `booking.PaymentAuthorized` (ch 10), and finalized by `booking.TripConfirmed`, or by
  `booking.TripCancelled` after `booking.FlightReservationCancelled` and a refund. State
  includes the trip request, the count of planning requests made (the latest is outstanding,
  and a proposal names it by `request_id`), the proposals received as event-carried state, the accepted
  proposal's id and itinerary rank, the count of questions asked per proposal, the status
  (new, requested, planning, proposed, awaiting clarification, approved, awaiting policy
  approval, reserving, reserved, confirmed, cancelled), the Traveler entities, the Reservation entities (status pending,
  hold, confirmed, or cancelled, hold expiry, supplier reference, the negotiated rate), from
  ch 8 the customer reference and the workflow's macro-state (`StateStore`) as part of
  this aggregate, and from ch 10 the Payment entity. The Trip as built through ch 3 holds
  the fields ch 3 uses (The state and its schema, below).
* **Proposal:** owned by the Itinerary Planner. Identified by a `proposal_id` generated by the
  Planner at publish time, keyed by the trip id; each
  `planning.ItineraryProposed` is the immutable answer, published under its own event id and
  carrying one to three ranked Itineraries with their items and offers; a re-request produces
  another proposal, re-planning the items the request does not name as carried over, and a
  request interrupted by a newer one is answered with `planning.ItineraryRequestSuperseded`.
  `booking.ItineraryApproved` marks the chosen itinerary. State: the requirements as they
  stood, the status (proposed or accepted), the itineraries, the chosen rank
  (01_system_overview.adoc, The Proposal).
* **Not aggregates of the spine:** the ApprovalRequest (policy, written by the approval
  console), the Customer and the Conversation (customer, written by the Front Desk), the
  Document (destination, written by the claim-check ingestion). The platform holds no aggregate;
  its guards keep their counters in the `GuardStateStore`.

=== The Trip's Operations

Drafted 2026-10-16 and settled with the author the same day. The aggregate above says what the
Trip holds; this says how it changes and who does what. Three parties, one verb each: **the Trip
decides**, **the store writes**, **the activator publishes**.

The Trip is one class in the Booking Agent's component (`components/booking_agent/booking_agent/trip.py`,
never in `travel_agency`, which holds only what components share), a Pydantic model whose fields are the trip's state and
whose methods are its operations, one per business action, each guarded by the checks that
keep the trip consistent (the invariants) and each returning the one event it produces. The
class depends on the event classes and the library's `Refused`, and on nothing else: it never meets the store, the broker,
the framework, or the LLM, which is what makes it testable as plain Python and what lets its
operations be handed to an LLM as tools. The word aggregate names this pattern once, for readers
who know Domain-Driven Design; the book otherwise says the Trip, the Trip's operations, the
Trip's rules.

The plumbing around the class is the activator's, not the agent's (settled 2026-10-20). The
Booking Agent declares its state beside its events,
`state = eda.state(Trip, key="trip_id", created_by=[TripRequested])`,
and for every activation the activator asks the store whether the event was already handled,
loads the Trip by the event's key, hands it to the agent with the event, and, when the agent
returns its event, commits the Trip with the version it loaded and the event's id, publishes,
and acknowledges (`04_implementation_design.adoc`, The Agent Activator). An **activation** of the
Booking Agent is therefore one operation call: `trip.approve(reply.proposal_id, rank)`.
On `booking.TripRequested` there is no Trip to load: the activator creates the row under the
request's event id first, so the Trip knows the id it will announce, hands the activation a
blank Trip with that id and nothing else, and the activation's `trip.open(request)` records
the request on it (amended 2026-10-24, when the code was built). A request that fails the
checks leaves the blank row in place, status `new`, with the request's event id recorded
against it, which is what lets a redelivered rejected request be recognised too; no trip
exists in the business sense, since nothing is ever planned for a `new` row. For the customer's reply the
LLM's tools are the Trip's reply operations themselves, bound to the loaded Trip for each LLM
call by the library's `StateOperations` (2026-10-27); the operation the LLM picks changes it in
memory and returns the event, a refusal (the library's `Refused`) returns to the LLM as the
tool's result,
and the activator commits once, after the activation returns that event. An operation the
agent's code calls that the Trip refuses is answered with `Nothing` and the refusal's reason:
the Trip changes only through this agent's own activations, one event at a time, so the same
event would be refused again, and the acknowledgement ends it. No operation and no
agent code publishes or touches the store; nothing in chapter 3 calls `eda.publish`, which
`04_implementation_design.adoc` introduces in chapter 7 for the reservation step.

Four rules hold for every activation:

* **One event per activation.** An activation answers with one event of a declared class, or
  `Nothing`, and the Booking Agent reaches its next step by consuming its own event:
  `booking.TripCreated` triggers the planning request, `booking.ItineraryRejected` and
  `booking.TripChanged` trigger it again. The audit record then shows each request caused by
  the event that made it necessary.
* **One cause, once.** The activator records the inbound event's id with the trip at commit. A
  redelivered event whose id is already recorded is acknowledged with no effect and no event
  produced a second time, before any agent code runs: deduplication by event id, built and
  named in chapter 3 and taught in full in chapter 10. Creation is the same rule on a different index: the request's event id is unique on the
  `trips` table, so a redelivered `booking.TripRequested` finds its trip.
* **One version.** The activator's commit carries the version it loaded, and the
  store refuses a stale one (the fence, `04_implementation_design.adoc`; built from chapter 3
  and taught in chapter 8).
* **One writer.** Only the Booking Agent's activations call the operations, and only the
  activator writes the row. The LLM proposes an operation by calling its tool; the operation
  decides.

The reply activation calls exactly one of `approve`, `reject`, `change`, or `request_clarification`. Checking the request,
creation, the planning request, and recording a proposal are activations with no LLM call. The cap is three: each question costs the customer a round trip of hours or days,
and after three the likelier fault is the proposal, not the words; a re-plan with the customer's
words as the reason serves them better than a fourth question. From chapter 8 the exit at the
cap is `booking.HandoffRequested`, the trip handed to a human agent beside the manager's
approval; until then the refusal forces the decision on the words (2026-10-27).

==== The state and its schema

The store keeps the Trip's state, saved as one JSON document: the class's fields serialised by the activator
(`trip.model_dump()`) on the way out and rebuilt (`Trip.model_validate`) on the way in, with
`schema_version` as one of the fields from chapter 3. As built through chapter 3 the fields
are `schema_version`, `trip_id`, `status`, `requirements`, `planning_requests`, `proposals`
(each with its id, its itineraries, and the count of questions asked about it), and
`approved` (the proposal's id and the rank). Within the book the state's shape changes by
addition only: a later chapter adds its fields with defaults (reservations empty, macro-state
absent, payment absent), so a row written by an earlier chapter loads unchanged. The rule
is the one chapter 14 teaches for events: an additive
change is a new optional field with a default, free at load; a breaking change bumps
`schema_version` and adds an upcast function the activator applies before validating, a read-time
migration, with rows never rewritten in bulk. The book makes no breaking change, so the
activator has no upcast step.

=== Stores and Read Models

* **The Trip's state:** the write model, kept for the Booking Agent by the activator in the
  `StateStore`, PostgreSQL from ch 3. Stores the trip id, the requirements, the status, the
  count of planning requests, the
  proposals received through `planning.ItineraryProposed` (event-carried state, immutable, so
  a copy cannot drift), the accepted proposal's id and itinerary rank, and from ch 7 the
  reservations. Changed by the Trip's operations, one per activation, on booking's requests,
  the agent's own events, planning's answers, and the edge observations. The Booking Agent
  never queries planning's store.
* **Proposal store** (designed, not built through ch 3; `01_system_overview.adoc`, The
  Proposal): maintained by the Itinerary Planner behind its store port. One table
  keyed by the proposal's id, with the trip id, the published event id, the request and
  publish times, the status, the chosen rank, and the requirements and itineraries as
  documents, indexed on trip id and request time; a trip's proposals are listed in the order
  of their requests. Updated by planning's own events and by `booking.ItineraryApproved`.
* **Semantic Views:** maintained by the Observer/Reflector Agent (ch 6) in the
  `SemanticViewStore`: `TripView` per trip, built from every topic and reconciled by causation,
  scoped by `contextpath`.
* **Audit Read Model:** maintained by the Audit Consumer. Appends every event, whole, as one
  line of JSON to a file (`AUDIT_LOG`) in arrival order; a workflow is read out of it by
  filtering on its correlation id.

There is no payment read model: the Payment entity lives on the trip, and the payment provider
adapter's `IdempotencyStore` holds request keys, not a model.

=== Example: A Trip Change During Planning

Scenario: the customer changes the dates while the Planner is composing the proposal.

1. **T1:** the Booking Agent commits `booking.TripChanged(trip_id=T-123, dates=14..17)`, key
   `T-123`, correlation id `CID-A`, and writes
   `planning.ItineraryRequested(id=R2, trip_id=T-123, carried_over=[flight])`, causation the
   change, on the planning topic.
2. **T2:** the Planner is mid-activation on request `R1` (key `T-123`).
   `planning.ItineraryRequested` is declared interrupting for that activation, so the running
   loop takes `R2` from its inbox between tool steps, publishes
   `planning.ItineraryRequestSuperseded(request=R1)` with causation `R2`, and restarts from its
   checkpoint with the new requirements, re-planning the stay only; had the activation already
   finished, `R2` would be handled in the next one and the trip would have two proposals.
   Either way the Planner publishes `planning.ItineraryProposed(trip_id=T-123)` answering `R2`,
   causation id `R2`, correlation id `CID-A` (inherited), key `T-123` on the planning topic.
3. **The Trip:** at T1, records the new dates and the outstanding request.
   At T2, receives the superseded fact and stops expecting a proposal for `R1`, then receives
   proposal `R2` and records it. **No conflict, because Trip and Proposal are separate
   aggregates.**

If Trip and Proposal were in the same aggregate, the two updates (one from the Booking Agent at
T1, one from the Planner at T2) would conflict. One would be rejected, or they would need to be
serialized. Keeping them separate means both proceed independently, and the read model
reconciles them via causation and the proposal's id.

== Design Decisions and Rationale

=== Why Not Atomic Transactions?

Atomic transactions (ACID) require all changes to commit or all to roll back. In a distributed
system with multiple writers, achieving atomicity requires consensus, a performance bottleneck.
The Travel Agency instead uses saga patterns: a component publishes an event, waits for
downstream effects, and publishes a compensating event if needed.

=== Why Not Pessimistic Locking?

Pessimistic locking (holding locks across multiple operations) is an alternative to eventual
consistency. A component could acquire a lock on Trip 123 before allowing the Planner to propose
for it. But locks are slow, do not scale, and are fragile (a dead component may hold a lock
forever). Per-key ordering gives the write side its serialization for free, and eventual
consistency covers the rest.

=== Why Not Real-Time Queries?

Instead of reading a stale read model, why not query the Trip's current state synchronously when
the Planner needs it? Because synchronous queries are coupled and slow. If the Booking Agent is
down, the Planner blocks. Event-driven systems separate concerns: the request carries what the
Planner needs, the Planner publishes its proposal, and downstream components react. The Planner
does not wait.

One kind of synchronous call across contexts is allowed, and the rule is drawn from the
boundary criteria of 2.2: a query whose answer is perishable and on which no other component
acts. The Planner reads the hotel sim's inventory over MCP and, from ch 5, asks the Research
Agent's tool, because a search result expires in minutes and nothing else reacts to it; if the Research Agent
is down the Planner degrades its proposal rather than blocking a workflow. A fact anyone else
acts on, or must be able to replay, goes on the broker.

=== Why Ordering in the Contract Rather Than an Order-Free Design?

An order-free design is possible: the writer assigns a sequence number per subject at commit
under a version check, state-carrying inputs resolve by highest sequence, and delta consumers
stage gaps. It is portable to any broker, and it is four mechanisms for the reader to hold at once.
Mandating brokers that order per key costs one condition on the topic mapping, one on the
consumer, and one fence in the store, and every broker likely to be found in an enterprise
qualifies.

=== Why Not a Payment Aggregate?

Payment is a step of booking behind a provider adapter. The adapter observes the charge and is
idempotent against the real side effect through its `IdempotencyStore`; the Booking Agent records
the outcome on the trip and confirms. A Payment aggregate would add a writer, a topic, and a
lifecycle to a fact already owned by the trip.

== Summary

The Travel Agency system is a **hybrid consistency model**: strong within aggregates, eventual
across them. It combines one writer per aggregate with its state in a store, immutable
facts for every change, CQRS (separated read models), ordering
by key in the broker contract (one lane per aggregate, one consumer at a time), and causation
tracking (explicit dependency chains). Each aggregate has a single writer, in-order delivery on
every supported broker, and an independent lifecycle. Idempotent projections handle
redeliveries. Out-of-order arrival is tolerated only across topics, where causation and staging
reconcile dependencies. The trade-off is that cross-aggregate queries and updates may lag and
must be compensated, but the system is resilient, scalable, and fast. What the activation
protocol leaves open before chapters 8 and 10 is registered above (The Activation Protocol).
