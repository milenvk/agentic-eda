= Travel Agency Application, System Design: Data Consistency and State Model
:toc:

// Design documentation for the Travel Agency application built across the book. Companion
// documents: 01_system_overview.adoc (components, domain map, identifiers),
// 02_workflows_and_events.adoc (workflows + events), 03_chapter_mapping.adoc (chapter mapping),
// 04_implementation_design.adoc (implementation surfaces and conventions). This document defines
// the architectural strategy for handling state, consistency, and ordering in a distributed,
// eventually-consistent system.

== Overview

This document describes how the Travel Agency system ensures consistency across its components
without requiring synchronous coordination. The strategy rests on four pillars: **Event
Sourcing** as the write model (immutable facts), **CQRS** (Command Query Responsibility
Segregation) to separate writes from reads, **ordering by key** as part of the broker contract
(an aggregate's events arrive in publish order), and **eventual consistency** across aggregates
enforced through causation tracking, staging, and idempotent read model updates.

== Event Sourcing: The Write Model

The system does not store aggregate state directly. Instead, every state transition is recorded as
an immutable event, the fact that it happened. An aggregate root is the entity whose events are
the source of truth for that aggregate's state.

* **Aggregates:** the spine has two aggregate roots, the Trip (booking) and the Itinerary
  (planning). Each event belongs to exactly one aggregate. A Trip's events name the trip id,
  which is the id of the `booking.TripRequested` event that created it; the Itinerary is keyed
  by the same trip id, one itinerary per trip, so `planning.ItineraryProposed` names the trip
  id too, on planning's topic. A payment is not an aggregate: the Payment is an entity inside
  the Trip, and `booking.PaymentRequested` and `booking.PaymentAuthorized` are trip events. The
  other contexts' aggregates (Customer and Conversation, ApprovalRequest, Document) follow the
  same rules with their own writers and topics; this document works through the spine.
* **Immutability:** events are written once and never modified. Correction is a new event
  (e.g., `booking.TripCancelled`), not an edit to an existing one.
* **Replay and Rebuilding:** the full history of an aggregate's events reconstructs its current
  state. If a read model is corrupted or stale, replaying the event log rebuilds it without loss
  of information.

== CQRS: Separation of Writes and Reads

CQRS does not mean the event log itself is separate from the command handler. It means the *model
used to answer queries* is separate and derived.

* **Write Model (Events):** agents publish facts, never commands. These events carry the fact (e.g.,
  "customer requested a trip for 2 travelers"). Once published, an event is immutable. It does
  not express an opinion about whether the request is valid; the event is the record of the fact
  that it was requested.
* **Read Model (Projected State):** a separate service or component listens to events and builds a
  materialized view, a queryable snapshot. For example, the Booking Agent maintains a read model
  saying "Trip 123 has status = 'requested', traveler count = 2". This view is mutable and can be
  rebuilt from scratch.
* **Eventual Consistency:** the read model lags behind the event log. When an event is published,
  the read model has not yet been updated. A subscriber listening for events and projecting them
  into the read model does so at its own pace. If the subscriber is fast, the lag is milliseconds;
  if congested, it may be seconds. But the read model eventually matches the history.

== Single Writer Principle: One Writer per Aggregate

Only one component (or one component's replica set, serialized by key) publishes the events
that change a given aggregate. The Booking Agent is the single writer for Trip events; the
Itinerary Planner is the single writer for Itinerary events. Two exceptions are part of the
principle, not violations of it:

* **The creating request.** `booking.TripRequested` creates the Trip rather than changing it, so
  any member of the booking context may publish it (the demo script in ch 1, the Booking Agent
  from ch 3, a partner adapter standing in booking). Every later fact about the trip has one
  writer.
* **Edge observations.** The Rental Car Agent's `booking.CarRentalReserved` and the payment
  provider adapter's `booking.PaymentAuthorized` are observations published by components at
  booking's edge. They are inputs to the Booking Agent, which records each with a fact of its
  own (`booking.CarReserved`, `booking.TripConfirmed`), causation set to the observation. The
  aggregate still has one writer.

This principle does not prevent reads. The Audit Consumer reads all events. The Booking Agent
consumes `planning.ItineraryProposed` to know what has been proposed (a read). But when the
Itinerary Planner revises its own Itinerary aggregate, only it publishes the next
`planning.ItineraryProposed`. The customer's decision on a proposal is booking's fact
(`booking.ItineraryApproved`, `booking.ItineraryRejected`), published by the Booking Agent and
consumed by the Planner. The two writers share a key value, the trip id, and share neither a
topic nor a writer.

=== Multiple Replicas of the Same Writer

The single writer principle does not require a single process. A component may have multiple
replicas for scaling or availability, and the ordering contract serializes them: the broker
assigns each key's lane (a Kafka partition, a Pub/Sub ordering key) to one replica of the group
at a time, so at any moment exactly one replica handles a given trip, and it handles that trip's
events one at a time, in order. No lock and no coordination protocol is needed.

The one gap is a rebalance. A replica in the middle of an activation when the broker reassigns
its lane can write after the new owner has moved on. The store's version check is the fence: a
write carrying a stale expected version of the aggregate is rejected, and the rejection returns
to the handler as an error (`04_implementation_design.adoc`). The demos never hit it; ch 8 states
it in one sentence.

== Causation Chains: Linking Events Across Aggregates

When one aggregate's event triggers a change in another aggregate, the two events are linked by
the **causation id** (`causationid`) and the **correlation id** (`correlationid`) extension
attributes.

* **Causation id:** when the Planner receives a `booking.TripRequested` event, it publishes
  `planning.ItineraryProposed` with `causationid` set to that event's id. The read model can
  trace backward: "this itinerary proposal was caused by this trip request." A re-plan carries
  the id of the `booking.ItineraryRejected` or `booking.TripChanged` that caused it.
* **Correlation id:** all events in a logical flow (e.g., all events related to planning a single
  trip request) share a correlation id. The first event in the flow (the trip request) mints
  a new correlation id; subsequent events inherit it. The audit log can then trace the entire
  workflow by correlation id. A second thread on the same trip (ch 8's duty of care, ch 9's
  disruption) mints its own.

Causation chains are stored in event `attributes` (see `04_implementation_design.adoc`). They
enable tracing without requiring real-time synchronous calls between components.

== Aggregate Boundaries: Why Trip and Itinerary Are Separate

A naive design might fold the Itinerary into the Trip, reasoning that there is exactly one
itinerary per trip and it is keyed by the trip anyway. This design is rejected because:

* **Different Writers:** the Trip is created and changed by the Booking Agent; the Itinerary is
  created and revised by the Planner. One aggregate would have two writers, or one writer
  relaying the other's decisions.
* **Concurrency:** a customer can change the request (`booking.TripChanged`) while the Planner
  is composing a proposal for the original one. In one aggregate the two updates conflict and
  must be serialized by a lock or a consensus step. As separate aggregates both proceed: the
  Planner's running activation receives the change through its activation inbox and re-plans,
  and the pairing of trip change and new proposal is explicit through causation and the
  itinerary's version.
* **Different Lifecycles:** the Itinerary is revised until accepted and then frozen as a version;
  the Trip lives on through reservation, confirmation, servicing, and cancellation.

The same reasoning decides the other boundaries. The Payment is *not* a separate aggregate: one
writer (the Booking Agent) records it, the provider adapter only observes, and the idempotency
against the real side effect lives at the adapter's `IdempotencyStore`, so a second aggregate
would add a lifecycle without adding a writer. The ApprovalRequest *is* separate, because a
different party (the manager, through the approval console) decides it and its record outlives
the trip's wait.

By keeping Trip and Itinerary separate, each maintains a single writer, a clear lifecycle, and
independent concurrency. Trade-offs:

* **Cross-Aggregate Reads:** the Booking Agent learns the current proposal from
  `planning.ItineraryProposed`, not from a synchronous call; its view may lag.
* **No Atomic Transactions:** a trip change and the proposal it causes cannot be made atomic.
  The change is published first; the proposal follows. If the proposal never arrives (a crash),
  the change is already committed and the trip waits, which is the durable state machine's
  normal condition (ch 8). Compensation is a saga (ch 9), never a rollback.

== Read Models: Materialized Views and Idempotent Projections

A read model is built by a **projection**, a component that listens to events and updates a
query-able store (a database table, an in-memory cache, a materialized view).

=== Idempotent Projections

Brokers guarantee at-least-once delivery, which means an event may be redelivered (e.g., if the
consumer crashed or was slow to acknowledge). A projection must be idempotent: applying the same
event twice produces the same final state as applying it once.

Example: a read model stores `trip_status`. When `booking.TripRequested` arrives with trip id 123
and status "requested", the projection updates the row for trip 123. If the same event is
redelivered due to a consumer restart, the projection receives it again. An idempotent projection
checks: "have I already processed this event?" If yes, skip it. If no, process and record it.

Idempotency is implemented via **event deduplication by event id**. Each event has a globally
unique id. The projection tracks which event ids it has processed. Before updating state, it
checks: "have I already processed event id X-Y-Z?" If yes, skip it. If no, process and record
the id. This is required for all consumers; the ordering contract makes a redelivery arrive in
order, not disappear.

=== Handling Out-of-Order Events: Across Topics Only

Within a key on one topic, order is guaranteed by the contract: all events for Trip 123 on the
booking topic are delivered in publish order, and the consumer's idempotency guard handles
redeliveries.

Out-of-order arrival occurs only *across topics*. The Booking Agent and the Planner both react
to `booking.TripRequested`, in parallel, and the Planner's `planning.ItineraryProposed` travels
on the planning topic. Two lanes carry the same key value, so nothing orders them against each
other: the proposal can reach the Booking Agent before the Booking Agent has recorded the trip
from its own topic, and a view joining both topics can see either first.

A robust read model handles this by **staging**, the `InboxStore` shape of ch 4, with the
causation id naming the prerequisite:

* If `planning.ItineraryProposed` arrives first, the projection stages it under the trip id
  until the `booking.TripRequested` named by its causation id has been applied, then applies it.
* If `booking.TripRequested` arrives first, the projection records the trip, and the proposal
  applies on arrival.

In both cases the final state is the same, because the prerequisite is explicit. A projection
that joins topics tolerates this arrival order; within a key on one topic, order is guaranteed.

== Consistency Guarantees: Within and Across Aggregates

The system guarantees:

* **Strong Consistency Within Aggregates:** events for a single aggregate (e.g., Trip 123) are
  delivered in order and processed serially, one at a time, by one consumer. The read model sees
  them in publish order. Combined with idempotency, this ensures an aggregate's view is always
  consistent with its event history. This holds on every supported broker (Ordering
  Guarantees, below); there is no adapter on which it does not.
* **Causal Consistency Across Aggregates:** if event A (in one aggregate) causes event B (in
  another), the causation chain (B's `causationid`) explicitly links them. Read models use it to
  stage and resolve dependencies regardless of arrival order.
* **At-Least-Once Delivery:** every event is delivered at least once. Exactly-once is not
  guaranteed (the broker delivers at-least-once, and retries on failure). Idempotent projections
  tolerate duplicates.
* **Durability:** once an event is written to the broker, it persists until the retention period
  expires (e.g., Kafka's log retention).

The system does NOT guarantee:

* **Immediate Consistency:** a query to a read model immediately after publishing an event may not
  reflect that event. The projection is still applying it. This lag is typically milliseconds but
  may be seconds if the projection is congested.
* **Total Ordering Across Keys or Topics:** events with different keys have no defined order
  (event A for Trip 1 and event B for Trip 2 may arrive in any order), and events with the same
  key on different topics have none either. Cross-topic read models stage by causation.
* **Atomic Multi-Aggregate Transactions:** updates to two separate aggregates cannot be made
  atomic. One succeeds and is durable; the other may fail. Compensating logic is required.

Clients must accept these trade-offs:

* After publishing a fact (e.g., a trip change), the client waits for the projected read model
  to reflect the change before considering the operation complete. This waiting is the
  "eventual" part.
* If a client needs to coordinate updates across two aggregates, it publishes the first, waits for
  the read model, publishes the second (if needed), and waits again. If the second fails, the
  first is already committed; a compensating event may be needed to revert it.

== Ordering Guarantees: The Contract

Within-aggregate order **is part of the `EventBroker` contract** (`ch02_agent_container`,
`ch02_delivery_guarantees`), though the frozen `publish` surface takes no key: the key is the
CloudEvents `partitionkey` extension attribute, on every event from the ch 2 practical, and the
adapter maps it to whatever its broker orders by. The contract sentence: *events sharing a
`partitionkey` are delivered in publish order, one at a time, to one consumer.* It promises
order per key, never partitions; partitions are one of the adapter's ways of keeping it.

The key is a group label, never a per-event ordinal: events sharing a key form one lane, and a
key unique per event is no order at all. There are no sequence numbers, no highest-wins
resolution, and no staging inside an aggregate; order is the transport's, per key, never the
consumer's by content.

Three conditions make the promise hold, each stated where it lives:

1. **All of an aggregate's events share a topic.** Ordering brokers order per key within one
   topic, so two events of one aggregate on two topics are unordered whatever their key. The
   adapter therefore maps one topic per context from the ch 2 practical, with the type inside
   the event and subscription by type filtered in the adapter (`04_implementation_design.adoc`).
2. **The container consumes one key at a time and commits in order** (the consumer rule in
   `04_implementation_design.adoc`).
3. **A version check in the store fences a stale replica** (Multiple Replicas, above).

Two mechanisms build the lanes:

**Partitions (Kafka, Redpanda, Azure Event Hubs, RabbitMQ Streams):** the adapter uses
`partitionkey` as the record key, so all events for a given aggregate hash into one of a fixed
number of physical logs. The broker delivers a partition in order and assigns the whole partition
to one replica of a group, ordering unrelated keys along with related ones.

**Ordering keys (Google Pub/Sub with ordering enabled, Azure Service Bus sessions, SQS FIFO
message groups):** the adapter uses `partitionkey` as the ordering key, the session id, or the
message group id, a logical lane per key value. The broker holds the next message for a key until
the previous one is acknowledged.

Both solve the reserve-and-cancel race the same way: `booking.FlightReserved` and
`booking.FlightReservationCancelled` travel on the booking topic with the trip's id as key,
arrive in order, and reach one replica. Both need the one-topic condition, since lanes are
scoped to a topic. A partition serializes strangers, so handlers behind per-key order stay fast
and slow reasoning sits where order is not needed (`04_implementation_design.adoc`,
head-of-line blocking).

=== Supported Brokers

The backends available to the book's adapters. Agents never learn which adapter is
underneath, and the guarantee is the same on every supported one.

* **Supported, ordering by key:** Kafka and Redpanda (record key); Azure Event Hubs (partition
  key; Kafka-compatible); RabbitMQ Streams (partitioning by key); Google Pub/Sub (ordering keys,
  enabled on the subscription); Azure Service Bus (sessions); AWS EventBridge only behind a FIFO
  SQS queue (message group id), at the cost of a hop; Redis Streams by sharding streams per key
  hash, one consumer group per shard.
* **Unsupported, no per-key order:** AWS EventBridge standalone, Azure Event Grid, RabbitMQ
  classic queues (per-queue order exists but not per key, and one queue per aggregate does not
  scale).
* **To verify at ch 15 planning:** Google Eventarc's ordering guarantee behind Eventarc Advanced,
  and the exact Redis Streams sharding; the ch 15 adapters are written only against brokers
  confirmed in the first list, and the book's list of replacement brokers (ch 1.5) is
  restricted to them.

**An adapter that cannot order by key is not an adapter of this book.** The port promises order
per key, so a backend without it is unsupported or reached through a workaround from the first
list; it never ignores the key silently.

=== Across Topics

Lanes stop at the topic boundary. The Booking Agent publishes trip events to the `booking` topic
keyed by the trip id; the Planner publishes itinerary events to the `planning` topic keyed by
the same trip id, by design, since the Itinerary is keyed by the trip. Same key value, different
topics: nothing orders one against the other, and a read model needing both (e.g., "Trip 123
with its proposed Itinerary") must join them.

Co-partitioning across topics is not the answer: lanes are per topic, a Kafka join would tie two
topics to identical partition counts and one consumer, and an ordering-key broker has no such
notion at all. In the Travel Agency system **the solution is causation and staging**:

1. The Planner reacts to `booking.TripRequested` directly; the request carries the trip's
   requirements, so the Planner reads no trip model before proposing.
2. The Planner publishes `planning.ItineraryProposed` with `causationid` pointing to the request
   (or to the `booking.ItineraryRejected` or `booking.TripChanged` that caused a re-plan), keyed
   by the trip id.
3. The Trip's own read model applies proposals as they arrive and stages a proposal that arrives
   before its prerequisite (Handling Out-of-Order Events, above).
4. Cross-topic views (the Observer's `TripView`, ch 6) are built from both topics and reconciled
   by causation, scoped by `contextpath` from ch 7.

This tolerates the out-of-order arrival of events from different topics without a global order.

== Broker Selection and Implementation Trade-offs

**No broker-specific code.** The design does not branch on broker type. A producer sets
`partitionkey` once and never learns which adapter is underneath. What used to vary with the
adapter, whether an aggregate's events arrive in order, no longer varies: every supported adapter
keeps the contract, and a projection may assume within-aggregate order everywhere. The ch 15
cloud chapter names its managed adapters, all from the supported list, so a reader
moving the system keeps the guarantee by construction.

== Application to the Travel Agency

=== Aggregates

* **Trip:** owned by the Booking Agent. Created by `booking.TripRequested`, whose event id is the
  trip id and the key; changed by `booking.TripChanged` (the customer changes the request),
  `booking.ItineraryApproved` and `booking.ItineraryRejected` (the customer's decision on a
  proposal, the approval naming the proposal's event id), `booking.FlightReserved`,
  `booking.HotelReserved`, `booking.ReservationFailed`, and `booking.CarReserved` (recording the
  Rental Car Agent's observation), `booking.ApprovalRequested` and `booking.ApprovalTimedOut`
  (ch 8), `booking.PaymentRequested` with the recording of `booking.PaymentAuthorized` (ch 10),
  and finalized by `booking.TripConfirmed`, or by `booking.TripCancelled` after
  `booking.FlightReservationCancelled` and a refund. State includes the trip request, the
  accepted itinerary version, the status, the Traveler entities, the Reservation entities
  (status pending, hold, confirmed, or cancelled, hold expiry, supplier reference), from ch 8 the
  customer reference and the workflow's macro-state (`WorkflowStateStore`) as part of this
  aggregate, and from ch 10 the Payment entity.
* **Itinerary:** owned by the Itinerary Planner. Keyed by the trip id, one per trip, with no id
  of its own. Each `planning.ItineraryProposed` is an immutable proposal identified by its own
  event id and carrying a version; the current itinerary is the latest proposal, and a re-plan
  (caused by `booking.ItineraryRejected` or `booking.TripChanged`, both booking's facts consumed
  by planning) produces the next version, re-planning the affected items only. State includes
  the version, the status, the requirements copied from the request, the rationale, the items
  with their offers, and the backup item.
* **Not aggregates of the spine:** the ApprovalRequest (policy, written by the approval
  console), the Customer and the Conversation (customer, written by the Front Desk shell), the
  Document (destination, written by the claim-check ingestion). The platform holds no aggregate.

=== Read Models

* **Trip Read Model:** maintained by the Booking Agent, in memory until ch 8 and in the
  `WorkflowStateStore` after. Stores the trip id, the request, the status, the reservations, the
  accepted itinerary version, and a reference to the current proposal (its event id). Updated by
  the Trip's own events and by `planning.ItineraryProposed` (via causation, staged when early).
* **Itinerary Read Model:** maintained by the Itinerary Planner. Stores, per trip id, the
  proposals by version and their status. Updated only by itinerary events.
* **Semantic Views:** maintained by the Observer/Reflector Agent (ch 6) in the
  `SemanticViewStore`: `TripView` per trip, built from every topic and reconciled by causation,
  scoped by `contextpath`.
* **Audit Read Model:** maintained by the Audit Consumer. Stores all events in arrival order,
  grouped by correlation id for tracing entire workflows.

There is no payment read model: the Payment entity lives on the trip, and the payment provider
adapter's `IdempotencyStore` holds request keys, not a model.

=== Example: A Trip Change During Planning

Scenario: the customer changes the dates while the Planner is composing the proposal.

1. **T1:** the Booking Agent publishes `booking.TripChanged(trip_id=T-123, dates=14..17)`, key
   `T-123`, correlation id `CID-A`.
2. **T2:** the Planner is mid-activation on the earlier `booking.TripRequested` (key `T-123`).
   `booking.TripChanged` is declared interrupting for that activation, so the running loop
   receives it through the activation inbox between tool steps and re-plans the affected items;
   had the activation already finished, the change would be handled in the next one. Either way
   the Planner publishes `planning.ItineraryProposed(trip_id=T-123, version=2)`, causation id =
   the `TripChanged` id, correlation id `CID-A` (inherited), key `T-123` on the planning topic.
3. **Projection (Trip Read Model):** at T1, records the new dates. At T2, receives the proposal
   with a causation id matching the already-applied change and records version 2 as the
   current proposal. **No conflict, because Trip and Itinerary are separate aggregates.**

If Trip and Itinerary were in the same aggregate, the two updates (one from the Booking Agent at
T1, one from the Planner at T2) would conflict. One would be rejected, or they would need to be
serialized. Keeping them separate means both proceed independently, and the read model
reconciles them via causation and the version.

== Design Decisions and Rationale

=== Why Not Atomic Transactions?

Atomic transactions (ACID) require all changes to commit or all to roll back. In a distributed
system with multiple writers, achieving atomicity requires consensus, a performance bottleneck.
The Travel Agency instead uses saga patterns: a component publishes an event, waits for
downstream effects, and publishes a compensating event if needed.

=== Why Not Pessimistic Locking?

Pessimistic locking (holding locks across multiple operations) is an alternative to eventual
consistency. A component could acquire a lock on Trip 123 before allowing the Planner to propose
for it. But locks are slow, do not scale, and are fragile (a dead component may hold a lock
forever). Per-key ordering gives the write side its serialization for free, and eventual
consistency covers the rest.

=== Why Not Real-Time Queries?

Instead of reading a stale read model, why not query the Trip's current state synchronously when
the Planner needs it? Because synchronous queries are coupled and slow. If the Booking Agent is
down, the Planner blocks. Event-driven systems separate concerns: the request carries what the
Planner needs, the Planner publishes its proposal, and downstream components react. The Planner
does not wait.

=== Why Ordering in the Contract Rather Than an Order-Free Design?

An order-free design is possible: the writer assigns a sequence number per subject at commit
under a version check, state-carrying inputs resolve by highest sequence, and delta consumers
stage gaps. It is portable to any broker, and it is four mechanisms for the reader to hold at once.
Mandating brokers that order by key costs one condition on the topic mapping, one on the
consumer, and one fence in the store, and every broker likely to be found in an enterprise
qualifies.

=== Why Not a Payment Aggregate?

Payment is a step of booking behind a provider adapter. The adapter observes the charge and is
idempotent against the real side effect through its `IdempotencyStore`; the Booking Agent records
the outcome on the trip and confirms. A Payment aggregate would add a writer, a topic, and a
lifecycle to a fact already owned by the trip.

== Summary

The Travel Agency system is a **hybrid consistency model**: strong within aggregates, eventual
across them. It combines event sourcing (immutable facts), CQRS (separated read models), ordering
by key in the broker contract (one lane per aggregate, one consumer at a time), and causation
tracking (explicit dependency chains). Each aggregate has a single writer, in-order delivery on
every supported broker, and an independent lifecycle. Idempotent projections handle
redeliveries. Out-of-order arrival is tolerated only across topics, where causation and staging
reconcile dependencies. The trade-off is that cross-aggregate queries and updates may lag and
must be compensated, but the system is resilient, scalable, and fast.
